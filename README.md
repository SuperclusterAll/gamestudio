# Autonomous Game Studio

기획 모델과 게임 코딩 모델로 게임을 제작하는 로컬 대시보드입니다.
HTML5 Canvas 단일 파일 또는 Godot 4 프로젝트 중 하나로 만듭니다.

**문서**: [아키텍처](docs/ARCHITECTURE.md) · [모듈별 설명](docs/MODULES.md) · [설계 판단과 근거](docs/DESIGN-DECISIONS.md) · [서비스 정의](SERVICE.md)

## 무엇을 푸나

지금은 아이디어 하나를 플레이 가능한 수준까지 만드는 데 2~3일이 걸립니다.
그 결과, 4개의 아이디어가 있어도 대부분은 플레이해 보지 못한 채 문서 단계에서 사라집니다.
우리는 이 시간을 2~3일에서 20분으로 단축합니다.
아이디어를 **문서가 아니라 플레이로 판단할 수 있게** 만드는 것입니다.

## 활용한 패턴 (Day 1~7)

- **Day 1: 도구 호출(Tool use)** — 코드 Agent에게 `write_game_file` · `read_game_file` · `generate_comfyui_image` 등 10종을 주고, **도구를 주는 것 자체를 가드레일로** 썼다. 이미지 쓰기 도구가 없으므로 이미지는 생성 도구로만 만들어진다.
- **Day 2: 구조화 출력(Structured output)** — 기획·구현 계약·QA 판정을 전부 Pydantic 스키마로 받는다. 계약 항목 수(8개)와 항목 길이(160자)를 **스키마가 강제**한다. 프롬프트로 부탁한 상한은 모델이 조용히 넘긴다.
- **Day 3: 멀티 에이전트(Supervisor)** — 기획·아트·코드·QA가 총괄 감독 노드를 허브로 오간다. 체인이 아니라 **엣지를 고르는 곳이 한 곳뿐**이라, QA 실패 시 아트로 되돌아가는 것도 별도 분기가 아니라 같은 허브의 다른 선택이다.
- **Day 4: 사람 개입(HITL)** — 기획 완료 시 `interrupt()`로 멈춘다. 이 대기 상태는 SQLite 체크포인트에 저장되어 **대시보드를 재시작해도 살아 있다.**
- **Day 5: 기억(Memory)** — 단기는 `ContextEditingMiddleware`로 도구 인자·오래된 결과를 지워 히스토리를 평평하게 유지하고, 장기는 셋이다: 출력 폴더의 `production-manifest.json`(최근 만든 게임 회피·채택·소비량), SQLite 체크포인트(승인 대기가 재시작을 넘김), **ChromaDB 아트 메모리**(이 스튜디오가 쓴 이미지 프롬프트).
- **Day 6: 계획과 재계획(Plan & Replan)** — 검증이 "이 물체에 그림이 없다"고 하면 아트를 **재수립**하고 → 생성 → 코드에 배선 → 재검증한다. 모델이 `code`를 골라도 코드가 `art`로 덮어쓴다(아래 회고 참조).
- **Day 6.5: RAG** — 아트 기획이 `visual_direction`으로 **자기가 쓴 프롬프트**를 조회해 예시로 받는다. 남의 스크린샷이 아니라 자기 산출물이라 저작권 문제가 없고, 질의·코퍼스·사람 라벨이 모두 있어 검색이 실제로 값을 한다 (아래 회고 참조).
- **Day 7: 평가(Evaluation)** — 고정 브리프 15케이스를 기획 단계에 통과시켜 7개 지표로 채점하고(`evals/`), 파이프라인 행동은 사람이 확인하는 20건 인-아웃 세트로 본다(`evaluation/test_queries.csv`). LLM 심사원을 쓰지 않는다 — 회귀와 잡음을 가르는 측정에 심사원 자신의 분산을 얹지 않기 위해서다.

## 현재 제작 방식

파이프라인은 총괄 감독(supervisor) 노드를 중심으로 한 허브 구조입니다.
각 단계는 끝나면 총괄 감독에게 돌아오고, 다음에 무엇을 할지는 총괄 감독만 결정합니다.

1. 장르와 플레이어 경험을 입력합니다. 빈 입력이면 기획 모델이 독자적으로 기획합니다.
2. 총괄 감독이 범위(무엇을 만들지 않을지)를 한 번 정하고, 기획·기획서 단계가 이를 따릅니다.
   기본값은 꺼짐이며 `DIRECTOR_TIMEOUT_SECONDS`로 켭니다.
3. 코드 모델이 핵심 규칙, 승패 조건, 상태 전환, 검증 기준을 구현 계약으로 작성합니다.
4. 사용자가 기획서와 구현 계약을 승인합니다.
5. 코드 모델이 원본 요청, 승인한 기획서, 구현 계약, 승인 메모에 따라 게임을 작성합니다.
   스프라이트가 필요하면 코드 Agent가 직접 ComfyUI 이미지를 생성합니다.
6. 2단으로 검증합니다. 1단은 모델 없이 결정론적으로 — HTML5는 키워드 스캔과 JavaScript 문법 검사,
   Godot은 프로젝트 구조 검사 후 엔진이 게임을 실제로 실행합니다.
   1단을 통과하면 2단에서 구현 계약과 대조하는 설계 감사를 수행합니다.
7. 검증에 실패하면 총괄 감독이 남은 예산 안에서 다음 조치를 고릅니다.
   기본 예산은 코드 Agent 재작업 2회, 아트 계획 재수립 1회, 그리고 HTML5에 한해 텍스트 수정 2회입니다.
   모두 소진하면 초안을 검토용으로만 배포하고 QA 미통과로 종료합니다.
8. 검증이 통과해야 완성본으로 저장하고 완료로 표시합니다.
   Godot은 프로젝트와 함께 `run.bat`을 만들며, 익스포트 템플릿이 있으면 웹 빌드도 생성합니다.

인증 오류, 기획 실패, 코드 미작성, 검증 실패를 고정 게임으로 대체하지 않습니다.
폴백 게임을 만드는 코드 자체가 없습니다. 실패는 실패로 보고합니다.
기획 일치 검증은 모델의 소스 코드 검토이며, 자동 브라우저 플레이테스트를 의미하지 않습니다.
그래서 수용 기준은 **소스만 읽고 판정할 수 있는 문장**이어야 하고, "육안으로 확인된다" 같은
관찰 주장은 스키마가 거부합니다 — 확인도 반증도 할 수 없는 기준은 언제나 통과하기 때문입니다.
다만 Godot 모드에서는 엔진이 게임을 헤드리스로 실제 실행하므로, 시작조차 하지 못하는 빌드는
모델에게 묻기 전에 파일과 줄 번호까지 특정해 걸러집니다.

## 모델 연결

로컬 AWS 프로필 또는 프로젝트 .env의 AWS 인증 설정을 사용합니다.
.env.example에는 실제 비밀 값을 넣지 않습니다. 인증 정보는 채팅이나 소스에 공유하지 마세요.
AWS 프로필, 역할, SSO 등 boto3의 인증 제공 경로를 확인합니다.
인증 설정 존재 여부와 선택한 Bedrock 모델에 대한 실제 접근 권한은 별개입니다.

대시보드에서 기획 모델과 게임 코딩·검증 모델을 각각 선택할 수 있습니다.
기본값은 기획·아트·코드가 Claude Sonnet 4.6, 검증·감독이 Claude Haiku 4.5입니다.
코드 작성 응답은 최대 32,000 출력 토큰을 요청하며 코드 Agent의 모델 호출은 런당 70회로 제한됩니다.
현재 환경에서 인증이 없으면 시작 요청은 503 오류와 설정 안내를 반환합니다.

CLI 예시:

```powershell
.\.venv\Scripts\python.exe -m game_studio.cli create --brief "방을 탐험하고 무작위 강화로 보스를 처치하는 로그라이크" --code-model-id global.anthropic.claude-sonnet-4-5-20250929-v1:0
```

## 산출물과 실행

각 실행은 `C:\dev\games\<제목>_<엔진>_<run-id>`에 격리됩니다 (예: `점령-미로_godot_175259532db8`).
런 id는 폴더 이름 맨 뒤에 고정되고, 조회는 **id로 폴더를 만드는 게 아니라 찾는** 방식입니다.

- draft.html: 작성/수정 중인 코드
- index.html: 검증을 통과한 게임
- production-manifest.json: 기획, 구현 계약, 검증 근거, 사용 모델
- assets/: 선택적 ComfyUI 이미지 및 아트 계획

게임 URL은 /games/<run-id>/ 입니다. /games/<run-id>는 후행 슬래시가 있는 주소로 이동합니다.
JS/CSS/이미지는 같은 게임 폴더 안에서 제공됩니다. 서버를 재시작해도 디스크의 게임은 열 수 있습니다.
승인 대기는 SQLite 체크포인트에, 완료된 실행 목록은 매니페스트에 남으므로 **재시작해도 유지됩니다.**

스튜디오 자신의 상태는 산출물과 분리해 프로젝트 안에 둡니다:

```
data/                          # git 무시 · 첫 실행 시 자동 생성
├── studio-checkpoints.sqlite  # LangGraph 체크포인트 (끝난 런은 시작 시 정리)
└── art-memory/                # ChromaDB — 이미지 프롬프트 기억
```

다른 PC에서 `git pull` 후 바로 실행하면 없는 것은 스스로 만듭니다. 별도 설정 단계가 없습니다.

## RAGAS 평가 결과

**해당 없음 — 이 프로젝트에는 RAG 파이프라인이 없습니다.** 검토한 뒤 의도적으로 넣지 않았으므로 RAGAS 지표도 없습니다.

넣으려다 만 것이 아니라 **재어 보고 기각한 것**이라, 그 근거를 대신 적습니다.

- **자동 기획에는 임베딩할 질의가 없습니다.** 사용자가 아무것도 안 썼다는 게 자동 기획의 정의라, 그 상태의 유사도 검색은 검색이 아니라 랜덤 샘플링입니다. 그럴 거면 `random.Random(seed)`가 더 정확하고 빠릅니다.
- **모델이 이미 압니다.** 검색이 값을 하는 건 모델이 *모를 때* — 사내 문서, 학습 이후 자료입니다. Tetris·Pac-Man은 가중치에 박혀 있습니다.
- **진짜 한계는 표 크기였습니다.** 실측하니 참조 표가 `6장르 × 3게임 = 18개`였고, 자동 기획의 변동 폭이 정확히 6가지였습니다. 검색 인프라를 붙여도 18개는 18개입니다.

그래서 **`15장르 × 87게임`으로 표를 키우고 런 시드가 3개를 샘플링**하게 했습니다. 실측 300회에 서로 다른 (장르+대표작) 조합 **266가지**가 나왔습니다 — 인덱스도, 임베딩 비용도, 재현성 저하도 없이.

검색이 필요한 자리가 하나 있었는데 그것도 벡터 DB로는 안 갔습니다: 브리프에 이름이 적힌 게임을 찾는 일입니다. 후보가 87개인 리터럴이라 **문자열 정규화**(공백·구두점 제거 + 짧은 이름 단어 경계)로 충분했고, 오탐 검증 17건을 통과했습니다. `src/game_studio/agents.py:_names`.

## 인-아웃 세트 통과율 (자체 평가)

평가 하네스는 `evals/briefs.json` **15케이스 · 7지표**로 구성돼 있고, 지표는 전부 결정론적입니다 (LLM 심사원 없음).

| 지표 | 무엇을 보는가 | 목표 |
|---|---|---|
| `genre_kept` | 요청한(또는 배정된) 장르로 왔는가 | 100% |
| `clone_named` | "테트리스처럼"에 테트리스를 댔는가 | 100% |
| `has_references` | 대표작을 하나라도 적었는가 | 100% |
| `genre_assigned` | 배정 장르가 참조 표에 행이 있는가 | 100% |
| `references_not_padded` | 지목한 게임에 다른 게임을 덧붙이지 않았는가 | 100% |
| `contract_sized` | 계약이 빌드 예산 안인가 | ≥80% |
| `tests_readable` | 수용 기준을 소스만 읽고 판정할 수 있는가 | ≥80% |

**전체 기준선은 아직 확보하지 못했습니다.** 15케이스 순차 실행이 약 15분이고 실제 모델을 호출하므로, 별도로 의도해서 돌려야 하는 작업입니다. 지금 있는 실측은 단건 시범 실행 하나뿐입니다:

```
1차 시범 (clone-tetris 단건) — 종합 75.0% · 61.7초
  clone_named 100% / genre_kept 100% / has_references 100% / contract_sized 0%
  계약 규모: mechanics 8 · acceptance_tests 8  ← 당시 상한 6
```

**이 한 건이 하네스를 만든 목적을 곧바로 증명했습니다.** 테트리스 요청은 제대로 반영됐는데 계약이 스키마 상한까지 꽉 차 있었고, 추적해 보니 **스키마(8)·프롬프트(8)·평가(6)가 서로 다른 숫자를 들고 있어** 유효한 계약이 매번 초과로 채점되는 상태였습니다. `CONTRACT_MAX_ITEMS` 하나로 통일해 고쳤습니다.

측정을 근거로 고친 항목은 아래 회고에 적었습니다. 전체 기준선을 뜨려면:

```powershell
.\.venv\Scripts\python.exe -m game_studio.evaluate --out evals/baseline.json
.\.venv\Scripts\python.exe -m game_studio.evaluate --baseline evals/baseline.json   # 이후 회귀 비교
```

## 트라이앤에러 회고

### 시도했다가 버린 것

**Deep Agents 감독.** `create_deep_agent`로 기획·아트·코드·QA 서브에이전트 4개를 둔 감독을 썼는데, **그 서브에이전트들의 시스템 프롬프트가 본 파이프라인과 같은 것**이었습니다. 감독이 `idea`에게 위임하면 진짜 기획 Agent가 돌고, 그 다음 `idea_node`가 또 돌았습니다 — **기획이 최대 12스텝에 걸쳐 두 번** 일어나고 첫 결과는 문단 하나만 남기고 버려졌습니다. 게다가 code 서브에이전트가 `CODE_SYSTEM`만 알아서 **Godot 런도 "standalone HTML game"으로 조율**됐습니다. 감독을 **범위 결정 단일 호출**로 바꾸고 `deepagents` 의존성을 제거했습니다.

**`create_supervisor`.** 구조는 이미 supervisor 패턴이지만 프레임워크는 안 썼습니다. 라우팅을 모델의 handoff 도구에 맡기면 **코드가 결정을 덮어쓸 자리가 없어집니다.** 실측된 실패가 있습니다 — "적에게 스프라이트가 없다"는 지적을 받은 모델은 거의 항상 `code`를 고르고, 코드 Agent는 아무도 계획 안 한 물체에 사각형을 그리고, 같은 지적이 다음 사이클에 돌아옵니다. 지금은 `_escalate()`가 모델 결정을 세 겹으로 감쌉니다: 예산이 남은 수만 메뉴에 올리고, 못 내는 수를 고르면 교체하고, **없는 그림을 요구하는 지적이면 무조건 `art`로 보냅니다.**

**요약 미들웨어(SummarizationMiddleware).** 토큰을 줄이려다 오히려 늘릴 뻔했습니다. 코드 루프의 가치는 같은 프리픽스를 50번 재사용하는 **프롬프트 캐싱**(캐시 읽기 0.1배)에 있는데, 요약은 오래된 메시지를 치환해 프리픽스를 바꿉니다 — 발동할 때마다 호출당 $0.0027이 $0.034가 됩니다. 게임은 디스크에 있으므로 요약본을 들고 다닐 이유가 없고, `ClearToolUsesEdit`로 **지우고 자리표시자를 남기는** 쪽이 맞았습니다.

**벡터 DB로 유명 게임 검색.** 위 RAGAS 절 참조. 다만 **이미지 쪽에는 진짜 공백이 있었습니다** — 아트 디렉터가 `image_prompt`를 아무 시각적 근거 없이 산문으로 씁니다. 그래서 소재를 바꿔 넣었습니다: 남의 스크린샷이 아니라 **이 스튜디오가 쓴 프롬프트**를 ChromaDB에 쌓고, 역할 9종·장르로 키를 잡고, 사람이 좋음/별로를 라벨링하면 좋은 프롬프트가 다음 기획에 예시로 들어갑니다. **그림이 아니라 말이 전이되므로** 같은 프롬프트를 써도 복제가 아니라 새 그림이 나옵니다. 저작권 문제도 없습니다 — `IDEA_SYSTEM`이 이미 "메커닉은 재현해도 되지만 아트는 가져오지 말라"는 선을 긋고 있었고, 유명 게임 스크린샷 RAG는 그 선을 넘습니다.

### 최종 채택한 것

**결정론적 검증을 모델 앞에 둡니다.** HTML5는 Node로 JS를 파싱하고, Godot은 **헤드리스로 컴파일한 뒤 실제로 5초 실행**합니다. 시작조차 못 하는 빌드는 모델에게 묻기 전에 파일과 줄 번호까지 특정해 걸러집니다. 모델 검토는 그 다음입니다.

**강제는 스키마와 코드로, 부탁은 프롬프트로.** 계약 항목 수·길이, 호출 예산, 재검토 횟수, 라우팅 덮어쓰기가 전부 코드입니다. *모델이 조용히 넘길 수 있는 상한은 예산이 아닙니다.*

**플레이 가능한 것을 먼저 저장합니다.** 호출 예산이 유한하므로 **디스크에 남는 것이 곧 출시본**입니다. 계약의 메커닉 순서가 빌드 순서이고 앞의 두 개만으로 이미 플레이 가능해야 합니다.

**실패해도 산출물을 내놓습니다.** QA 미통과 런도 프로젝트·런처·미해결 목록을 함께 배포합니다. 리뷰어는 시작할 수 있는 게임만 판단할 수 있습니다.

### 남은 한계

- **평가 전체 기준선 미확보** — 위 참조. 15케이스 순차 15분이고, 케이스끼리 독립이라 병렬화하면 3분 안쪽입니다.
- **계획 준수가 GDScript 실력보다 문제** — Godot 실패를 추적하면 문법이 아니라 `.gd`는 썼는데 `.tscn`을 안 만드는 식의 **자기 계획 미준수**였습니다. 모델을 올려도 얼마나 나아질지는 불확실합니다.
- **채택률 미측정** — 재개발 요청이 자동 기록되도록 붙였지만 표본이 아직 없습니다.
- **아트 메모리 표본 부족** — 장르당 스프라이트가 아직 한 자릿수입니다. 예시로 쓸 만하려면 장르당 좋은 것이 2~3개는 모여야 하고, 런 10~20회는 더 돌아야 합니다.
- **웹 빌드는 환경 의존** — Godot 익스포트 템플릿(~1GB)이 있어야 브라우저 임베드가 됩니다. 없으면 건너뛰고 프로젝트만 냅니다.
