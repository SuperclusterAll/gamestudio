# 설계 판단과 근거

**왜 그렇게 만들었는가.** 대부분 실제로 겪은 실패나 실측에서 나왔고, 그 근거를 같이 남긴다.
시스템 구조는 [ARCHITECTURE.md](ARCHITECTURE.md), 파일별 책임은 [MODULES.md](MODULES.md).

---

## 1. supervisor 패턴을 직접 구현한 이유

`langgraph-supervisor`의 `create_supervisor`를 쓰지 않았다.

**토폴로지는 supervisor 패턴이 맞다.** 허브-스포크, 라우팅 권한 단일화, 모든 워커가 허브로 복귀.
갈리는 지점은 패턴 여부가 아니라 **라우팅을 누가 결정하느냐**다.

`create_supervisor`는 handoff 도구(`transfer_to_<agent>`)로 LLM이 다음 워커를 고른다.
구조상 모든 hop이 모델 호출이다. 실측하면 지금 구조는 이렇다.

| supervisor 진입 | 다음 단계 | 모델 호출 |
|---|---|---|
| 첫 방문 | idea | **1** |
| idea 완료 | design_document | 0 |
| design_document 완료 | approval | 0 |
| approval 승인 | art | 0 |
| art 완료 | code | 0 |
| code 완료 | qa | 0 |
| qa 통과 | package | 0 |
| repair 완료 | qa | 0 |

**8회 방문에 1회.** (+ QA 실패 시 1회) 나머지는 `_NEXT_AFTER[stage]` 딕셔너리 조회다.

바꾸면 얻는 것과 잃는 것:

| | |
|---|---|
| ✅ 토폴로지 | 이미 같음 |
| ✅ QA 실패 시 LLM 판단 | 이미 있음 (`_decide`) |
| ➕ | 결정할 게 없는 hop 6개에 모델 호출 추가 |
| ➖ | 타입 state 계약 상실 — handoff는 공유 `messages`로 넘김 |
| ➖ | `interrupt()` 기반 durable 승인 게이트 |
| ➖ | **코드 수준 예산 강제** |

마지막이 가장 크다. 지금은 rethink가 소진되면 `code`가 선택지에서 **사라진다.**
프롬프트에 "쓰지 마세요"라고 적는 것과 다르다.

측정된 런에서 토큰의 85%가 입력이었다. hop마다 누적 대화 이력을 재전송하는 건 방향이 반대다.

**바꿀 값이 생기는 경우**: 단계 순서 자체가 런타임에 정해져야 할 때. 그때는 `_NEXT_AFTER` 테이블이
성립하지 않으므로 LLM 라우터가 필요해진다.

## 2. 검증은 막을 수 있는 것만 막는다

한 런이 **미해결 31건**을 안고 종료했다. 파고들어 보니 판정 로직에 버그가 있었다.

```python
rejected_ratio = len(rejected) / max(1, len(requirements))
```

`rejected`에는 리뷰어가 **우리가 묻지도 않은 요구사항을 스스로 지어내 거부한 것**까지 들어갔다.
계약을 의역해 자기 표현으로 실패시키면 비율이 1을 넘을 수도 있었고, 정작 실제 계약은 다 충족한
빌드가 차단됐다.

**고친 것**:
- `_verdict()`가 **우리 계약과 실제로 매칭된 것만** 집계
- 리뷰 프롬프트를 "요구사항마다 근거"에서 "**거부한 항목만** 근거"로
- "기타 발견사항"은 계약 위반이 아니라 의견 → 차단하지 않고 5건까지만 기록
- `QA_REJECT_TOLERANCE` 0.34 → 0.5

### 같은 원칙의 다른 적용

**미사용 스프라이트를 차단에서 기록으로 내렸다.** 게임은 돌아간다. 잃은 건 아트 비용이다.
차단하면 rethink 예산을 전부 태우고 **결국 그 지적을 안은 채 배포**한다 — 막지도 못하고 고치지도 못한다.

**키워드 검사는 전부 참고로.** `restart()` 버튼이 있는데 "재시작 없음"으로 읽혀 멀쩡한 게임을
떨어뜨린 적이 있다. 다만 **사실 기반 지적은 항상 표시**한다 — 디스크 위 파일에 대한 사실이지
키워드 추측이 아니다.

## 3. 스트리밍 누적이 2차였다

`gathered = gathered + piece`. 모든 LangChain 예제의 모양이고, 이 길이의 답변에는 함정이다.

`+` 마다 `AIMessageChunk`가 새로 생성되고, 생성할 때마다 `init_tool_calls`가 **누적된 툴 인자
전체를 다시 파싱**한다. 코드 Agent는 게임 한 편을 툴 인자 하나로 쓴다.

실측 (`write_game_file` 호출 모양, 40자 청크):

| 게임 크기 | 청크 | 변경 전 | 변경 후 | |
|---|---|---|---|---|
| 8,000자 | 201 | 0.111s | 0.0003s | 402× |
| 16,000자 | 401 | 0.578s | 0.0009s | 627× |
| 24,000자 | 601 | **1.112s** | **0.0007s** | 1593× |

모델이 말을 다 끝낸 뒤에 우리 루프가 태우던 CPU다. 빌드 1회 + 매 repair, 코드 Agent 턴마다.

`StreamAccumulator`가 조각을 리스트에 append하고 **마지막에 한 번만** 조립한다.
잘린 인자의 partial-JSON 복구는 그대로 유지된다 — 그건 잘림을 정직하게 보고하는 데 필요하다.

> 이 문제를 처음 만난 건 테스트 하나가 **31분 6초** 걸렸을 때다. 파스 불가능한 문자열 400청크로
> 부분 JSON 파서의 최악 경로를 탔다. 고친 뒤 같은 스위트가 8초에 끝난다.

## 4. 검증과 판단을 Haiku로

설계 감사는 **완성된 게임과 배포 사이에 그대로 놓여 있다** — 지연이 끝에서 끝까지 체감되는
유일한 단계다. 그런데 하는 일은 저작이 아니라 판단이다. 읽고 짧은 판정을 낸다.

Sonnet은 검사만 하면 되는 코드에 대해 수천 토큰짜리 에세이를 썼다. Haiku 4.5가 같은 질문에
몇 배 빠르게, 훨씬 싸게 답한다.

**같이 고친 정합성 버그**: 가격표에 Sonnet 4.6밖에 없었다. QA를 Haiku로 옮겼으면 대시보드 비용
추정이 **전체 런에 대해 조용히 `priced: false`** 로 바뀔 뻔했다. 대시보드가 제공하는 모든 모델의
가격을 넣고 테스트로 고정했다.

## 5. 프롬프트 캐싱

측정된 런에서 토큰의 85%가 입력이었는데 캐싱을 전혀 안 쓰고 있었다.

코드 Agent는 매 호출마다 [시스템 프롬프트 + 도구 정의 7개(~2,700토큰) + 누적 대화]를 다시 보낸다.
앞부분은 **한 런 내내 바이트 단위로 동일**하다.

실측 (실제 Bedrock 호출):

| 호출 | 입력 토큰 | 캐시 읽기 |
|---|---|---|
| 1회차 | 5,401 | 0 |
| 2·3회차 | 5,401 | **5,061** |

캐시 읽기는 입력 단가의 1/10이다. 20회 루프면 입력의 약 94%가 캐시가 된다.

**Anthropic 모델에만 적용한다.** Nova는 cachePoint 위치 규칙이 달라 잘못된 조합이 무시가 아니라
**API 거부**로 돌아온다. 비용 최적화가 런을 죽일 수 있으면 안 된다.

비용 추정도 같이 고쳤다. 캐시 읽기를 정가로 세면 **캐싱이 만들어낸 바로 그 상황에서 추정이
틀리고**, 캐싱이 작동하는지도 안 보인다.

## 6. 결정론적 검증은 모델 호출 없이 끝낸다

`write_game_file`이 예전엔 "다음으로 `run_static_qa`를 호출하세요"라고 안내만 했다.
그런데 `static_qa`는 모델 호출이 없고 내용별 캐시까지 된다. **쓰기 시점에 이미 알 수 있는
답을 물어보려고 턴을 하나 쓰는 것**이다.

빌드 루프가 write→qa→repair→qa 구조라 왕복이 두 배가 됐다. 이제 쓰기/수정 결과에 판정이 실려 온다.

Godot의 `run_godot_qa`는 엔진을 실제로 돌려 수십 초가 걸리므로 분리를 유지한다.

같은 이유로 `generate_asset` 도구를 제거했다. 아트 계획을 파일로 저장할 뿐인데 **도구 슬롯과
설명 토큰을 매 호출 차지**했다. 그래프에서 직접 쓴다.

## 7. state에 넣지 않는 것

코드 Agent 전체 대화가 그래프 state에 들어가고 있었는데 **읽는 곳이 한 군데도 없었다.**
에이전트는 매번 자기 payload를 새로 만들고, 대시보드는 `public()`에서 제외한다.

그 안에 `write_game_file` 인자, 즉 게임 전체가 들어 있어 체크포인트마다 재직렬화됐고
rethink마다 누적됐다. 빌드에서 런이 필요로 하는 것은 디스크에 있다.

`trace_notes`도 상한이 없었고 총괄 감독 브리프 전문이 그대로 들어갔다. 요약 + 최근 24개로 제한.

## 8. 승인 게이트의 지속성

`interrupt()` + 체크포인터는 "며칠 뒤 재개"를 위한 구조인데, 실제로는 `InMemorySaver`였다.
**프로세스가 죽으면 대기 중인 승인이 사라진다.** 완성된 게임은 디스크에서 살아남지만 그건
파일이지 실행 상태가 아니다.

SQLite로 바꾸고 검증했다:

```
1) 승인 대기 진입: ('approval',)
2) 재시작 후:      ('approval',)   기획서 제목: 지속성 테스트
```

DB를 못 쓰는 환경에서는 메모리로 조용히 떨어진다 — 영속성은 가질 만하지만 **그것 때문에
실패할 만하지는 않다.**

## 9. 자동 기획이 같은 게임만 만들던 문제

자동 기획으로 3번 돌렸더니 3번 다 별똥별 게임이었고 둘은 제목까지 같았다.

코드 버그가 아니라 **프롬프트가 출력 공간을 붕괴시킨** 것이다.

```
auto 일 때 참조 게임: ''        ← 빈 문자열
슈팅 일 때        : Space Invaders / Galaga / Geometry Wars
```

`GENRE_REFERENCES`가 장르로 키가 잡혀 있어 장르를 안 고르면 **대표작도 안 붙는다.**
자유롭게 들리지만 실은 반대다. 앵커가 사라진 자리에 나머지 제약만 남는다 — 단일 캔버스 파일,
60~120초 세션, 경쟁할 점수 지표, 소극적 플레이 처벌, 검증된 루프 차용. 그 교집합의 "가장 뻔한 답"이
떨어지는 물체 + 콤보 배율이다.

`Run seed`가 이걸 막으라고 있었는데 막을 수가 없었다. **프롬프트 속 헥스 문자열은 샘플링 시드가
아니다.** 모델이 그걸로 다른 설계를 만들 방법이 없다.

**고친 것**: 시드를 해시해 장르 하나를 배정한다. 그러면 시드가 원래 하려던 일을 한다 —
다른 시드는 다른 게임, 같은 시드는 같은 게임. 그리고 배정된 장르의 대표작이 같이 붙는다.

수정 후: 퍼즐(Tetris+2048), 퍼즐(2048 입력), 액션 생존(Vampire Survivors 루프).

### 9-1. 그래도 출력이 6가지였다 — 표 크기가 한계였다

장르 배정은 맞는 수였지만, 표가 **6개 장르 × 3개 게임 = 18개**였다. 자동 기획의 변동 폭이 정확히
6가지였다는 뜻이고, 한 장르 안에서는 늘 같은 대표작 3개로 출발했다.

여기서 "유명 게임을 벡터 DB로 검색해 붙이자"는 안이 나왔지만 **쓰지 않았다**. 자동 기획에는
임베딩할 질의가 없다 — 플레이어가 아무것도 안 썼다는 게 자동 기획의 정의다. 그 상태의 유사도
검색은 검색이 아니라 랜덤 샘플링이고, 그럴 거면 `random`이 더 정확하고 빠르다. 게다가 모델은
Tetris를 이미 안다. 검색이 값을 하는 건 모델이 모를 때 — 사내 문서, 학습 이후 자료다.

**고친 것 셋**:

| | 전 | 후 |
|---|---|---|
| 표 크기 | 6장르 × 3게임 = 18 | **15장르 × 5~7게임 = 87** |
| 장르 안 | 고정된 3개 | 런 시드로 **3개 샘플링** |
| 조합 수 | 6 | 수백 |

시드가 장르뿐 아니라 그 안의 대표작 조합까지 고른다. 같은 시드는 같은 조합을 재현하고, 다른
시드는 같은 장르라도 다른 자리에서 출발한다. 인프라 없이 리터럴 하나로 끝나는 일이다.

### 9-2. 시드가 플레이어를 덮어쓰고 있었다

평가 하네스를 붙이고 나서 실측으로 잡힌 버그다.

```
플레이어가 쓴 요청 : 블록을 회전시켜 빈틈없이 쌓는 게임을 만들어줘
시드가 배정한 장르 : 플랫포머
붙는 참조 게임    : Super Mario Bros / Celeste / Doodle Jump
```

**테트리스를 묘사했는데 마리오가 붙었다.** `자동 기획`은 드롭박스 기본값이라, 장르를 안 건드리고
브리프만 쓰는 흔한 조작이 전부 여기로 떨어진다. 그때 시드가 플레이어의 문장을 덮어썼다.

**고친 것**: 브리프에 사람이 쓴 문장이 있으면 `resolve_auto_genre`는 아무것도 배정하지 않는다.
대신 `infer_genre`가 그 문장을 읽는다 — 이름 댄 게임이 있으면 그것으로 즉시 결정하고(한글 표기
포함, "팩맨"도 잡힌다), 없으면 루프 단어가 **2개 이상** 맞는 장르를 고른다. 하나는 우연이고
("점프"는 슈팅 브리프에도 나온다) 둘은 묘사다. 못 고르겠으면 **아무것도 안 붙인다** — 틀린 행을
붙이는 게 위 버그 자체였으므로, 추측하지 않는 쪽이 낫다.

여기가 이 프로젝트에서 유일하게 "질의가 있는" 지점이지만 역시 벡터 DB를 쓰지 않았다. 후보가
87개인 리터럴에 임베딩 인덱스를 붙이면 동기화 대상과 실행 간 분산이 하나씩 늘 뿐이고, 정확도는
문자열 매칭보다 나을 게 없다.

프롬프트 문구도 갈라놨다. 플레이어 요청이 없으면 대표작은 **고르라는 메뉴**로 들어가고, 요청이
있으면 **참고 자료**로 들어간다 — "요청에 어긋나는 것은 무시하세요". 메뉴로 주면, 테트리스를
요청받은 모델이 목록에서 가장 가까운 게임을 고르는 쪽으로 샌다.

**장기 기억도 추가했다.** 같은 장르 안에서는 여전히 같은 설계로 간다 — 지난번에 뭘 만들었는지
알 방법이 없으니까. 매니페스트에 이미 기록돼 있으므로 **출력 폴더 자체가 기억**이다.
별도 저장소도, 마이그레이션도 없다.

## 10. 사용자 요청이 최우선

"테트리스랑 완전히 똑같은 게임을 만들어줘"에 다른 게임이 나왔다. 프롬프트를 찍어 보니 셋이
동시에 반대로 밀고 있었다.

| 출처 | 지시 |
|---|---|
| 최근 산출물 회피 | "이것들과 **뚜렷하게 다른** 게임을" ← 조건 없이 적용 |
| `IDEA_SYSTEM` | "최대 하나의 변형만 더하라" |
| `IDEA_SYSTEM` | "독립된 **original work**여야 한다" |

첫 번째가 특히 문제다. **다양성은 요청이 없을 때 최적화할 값이지 요청에 맞서 쓸 값이 아니다.**
지난주에 퍼즐을 만들었다는 이유로 "테트리스 만들어줘"에 "다른 걸 만들라"고 답하고 있었다.

`player_requested()`가 사람이 직접 쓴 브리프인지 판별하고, 요청이 있으면 회피를 적용하지 않으며
"위 요청이 다른 모든 지침보다 우선"을 명시한다. `IDEA_SYSTEM` 맨 앞에도 같은 원칙을 두어
시스템 프롬프트와 사용자 프롬프트가 싸우지 않게 했다.

결과: 7종 테트로미노, 회전, 하드드롭, 줄 제거, 레벨별 낙하 속도, 다음 조각 미리보기.

## 11. 아트 — 계획과 생성의 분리

`art` 노드는 그림을 그리지 않는다. 목록만 쓴다. 실제 생성은 code가 한다.

**왜**: art는 코드가 존재하기 전에 컨셉만 보고 계획한다. 코드 Agent는 만들면서 필요를 발견한다.
미리 뽑으면 (1) 틀린 계획에 예산을 태우고, (2) 직렬 대기가 생기고, (3) 무엇보다 **방향을 모른다.**

**예외**: 재수립일 때는 art가 직접 생성한다. 그 시점의 객체는 이미 결정돼 있다 — 검증이 지목했다.
발견할 게 없다. 그리고 코드 Agent 루프 안에서 생성하면 코딩과 경쟁한다.

> 실측된 실패: 한 런이 호출 4개를 스프라이트 생성에 쓰고 **연결할 호출이 남지 않았다.**

파이썬 함수 직접 호출이라 **모델 호출 0회**다. 방향은 `sprites.json`에서 기존 스프라이트의
방향을 읽어 이어받는다 — 재수립 시점엔 게임이 이미 있어 카메라가 정해져 있다.

### 강제 3단

재수립이 목록에 항목을 추가해도 코드 Agent가 건너뛰면 **같은 지적이 다음 사이클에 돌아온다.**
그래서 `required_assets`는 메뉴가 아니라 의무다.

1. 프롬프트에 "MANDATORY ART" 명시
2. 코드 Agent 자기 검증 도구가 통과를 거부 (예산 남았을 때 잡는 자리)
3. 그래프 QA 백스톱 (예산을 다 써서 멈춘 경우)

단, **이미지 생성이 꺼진 런에는 의무를 주지 않는다.** 아무도 만들 수 없는 것을 요구하면
남은 사이클이 전부 고칠 수 없는 지적에 막힌다.

## 12. 스프라이트 배경 제거

ComfyUI의 `RemoveBackground` 노드는 있지만 `background_removal` 모델 폴더가 **비어 있다.**
(익스포트 템플릿과 같은 상황) 그래서 파이썬 쪽에서 잘라낸다 — 장당 **0.8초**, 생성 40초에 비하면 공짜다.

**1차 시도가 실패했다.** "단색 배경"만 요청했더니 모델이 **어두운 배경**을 골랐고, 차체도 어두워서
플러드 필이 차체를 관통했다. 배경색을 모델에 맡기면 안 된다.

**2차도 실패했다.** 크로마키를 요구하고 순수 `#00FF00`과의 거리로 판정했더니, 실측 배경이
`(6,224,10)` · `(22,254,91)` · `(117,212,113)` — 명백히 초록인데 순수 키와는 멀어서 멀쩡한 컷을 버렸다.

**최종**: 판정을 "**초록이 지배적인가**"로, 픽셀 비교는 **모델이 실제로 칠한 배경색** 기준으로.
색 + 연결성 둘 다 본다.

> 중간에 만난 함정: `Image.fromarray`가 **readonly** 이미지를 돌려주고 floodfill의 쓰기가
> 조용히 버려진다. 채워도 `getpixel`이 옛 값을 반환한다. 중간 숫자가 전부 정상이라
> 실제 생성 두 라운드를 태우고서야 찾았다. `.copy()` 한 줄.

**남은 제약**: 외곽선 없이 배경 초록과 바로 맞닿은 초록 피사체는 같이 잘린다. 도구 설명에
"밝은 초록 객체는 요청하지 말 것"을 명시했다.

## 13. Godot 모드

### 웹 익스포트를 전제하지 않는다

`web_nothreads_{debug,release}.zip` 템플릿이 필요한데 Godot은 이걸 **전 플랫폼 묶음(약 1GB)**
으로만 배포한다. 편집기가 있는 머신도 템플릿은 없는 경우가 매우 흔하다.

그래서 **프로젝트가 산출물**이고 웹 빌드는 보너스다. 템플릿이 없으면 그 사실을 정확히 설명하고
`run.bat`으로 실행할 수 있게 한다. 템플릿이 설치되면 코드 수정 없이 웹 빌드가 켜진다.

### `repair`가 없다

`repair`는 게임 전체를 텍스트 한 덩어리로 돌려받는 모델 호출 1회다. HTML에겐 완성품이지만
`project.godot` + 씬 + 스크립트로 이뤄진 프로젝트에겐 무의미하다. 파일을 여러 개 쓸 수 있는
코드 Agent 루프로만 고친다.

부작용: `MAX_RETHINK_CYCLES=1`이면 **실질 재시도가 한 번**이다. HTML은 두 번.

### 엔진이 못 보는 것

엔진은 던져지는 것만 본다. `func _ready(): pass`뿐인 프로젝트는 아무것도 안 던진다 —
임포트되고, 5초 돌고, exit 0이고, **통과로 보고됐다.** 입력도 점수도 승패도 없는데.

`static_project_qa`가 그 자리를 메운다. 특히 `res://` 경로 실재 확인은 엔진이 못 하는 일이다 —
5초 헤드리스 실행은 **그때 지나간 코드 경로만** 건드린다. 입력이 필요한 분기의 `load()`는
절대 안 열리고, 깨진 경로가 플레이어 PC에서 처음 드러난다.

### WASD를 차단하지 않는 이유

웹에서는 진짜 결함이다 — `event.key`가 레이아웃 의존이라 한글 IME에서 W가 'ㅈ'로 온다.
하지만 **Godot의 `physical_keycode`는 레이아웃 독립**이라 그 버그가 성립하지 않는다.
방향키만 쓰는 건 설계 선택이지 고장이 아니다.

## 14. 오탐이 예산을 태운 사례

테트리스 런이 이렇게 끝났다.

```
QA 검증 — 엔진 검증 실패: 생성된 스프라이트를 프로젝트가 참조하지 않습니다:
          block-i.png, block-l.png, block-o.png
총괄 감독 — 수정·재검토 예산을 모두 사용했습니다
QA 검증 — 미해결 1건이 남은 상태로 게임을 배포합니다
```

재현해 보니 **제 검사의 오탐**이었다. 테트리스는 조각을 루프로 다룬다.

```gdscript
func texture_for(kind: String) -> Texture2D:
	return load("res://assets/block-" + kind + ".png")
```

리터럴 `"block-i.png"`가 소스 어디에도 없다. 문자열 일치만 보는 검사는 **스프라이트를 완벽하게
쓰고 있는 게임**을 "참조하지 않음"으로 판정했다. 정상 작성 방식 3종이 모두 오탐이었다.

두 번째 오탐이 겹쳐 있었다. 소스에 남는 조각 `res://assets/block-`을 "존재하지 않는 리소스"로도
잡았다. 파일명이 아니라 경로의 왼쪽 절반인데.

**고친 것**:
- `res://` 경로를 조립하는 코드가 하나라도 있으면 미사용 보고를 **아예 하지 않는다**
- 공통 접두사(`block-`)가 소스에 등장하면 사용 증거로 인정
- 확장자가 없거나 `%{}$*`가 섞인 참조는 리소스 검사에서 제외
- 미사용 아트를 차단에서 **기록으로** (§2)

**교훈**: 읽어서 알 수 없는 것에 대해서는 침묵하는 게 낫다. 틀린 "낭비했습니다"는 rethink 한
바퀴를 태워야 반증된다.

## 15. RAG를 쓰지 않는 이유

검토했고, 이 구조에서는 값을 하는 자리가 없다.

| 필요한 지식 | 판단 |
|---|---|
| Canvas API, GDScript 4 문법 | ❌ 모델 가중치에 있음 |
| 프로젝트 자체 코드 | ❌ 게임 하나가 5~20KB. 통째로 넣어도 되고 부분 읽기도 있음 |
| 과거 만든 게임들 | ⚠️ 이건 RAG가 아니라 **few-shot 템플릿** |
| 최근 산출물 회피 | ✅ 필요하지만 **파일 목록 읽기**로 충분 (§9) |

vector DB가 값을 하려면 사람이 못 고를 규모(수백 장 이상)의 **보유 라이브러리**가 있어야 한다.
이 파이프라인은 자기 아트를 스스로 생성한다. 뒤질 라이브러리가 없다.

스프라이트 스타일 일관성도 검색이 아니라 **고정 참조**(IP-Adapter/img2img)의 문제다.
후보가 하나뿐이니 유사도 검색이 개입할 자리가 없다.

사용자가 없는 게임을 있다고 믿게 된다.

## 17. 아직 안 한 것

의도적으로 남겨둔 것들.

**부분 편집 도구 (`replace_lines`)** — 지금은 한 줄을 고쳐도 게임 전체를 다시 생성한다.
출력 토큰이 크고 회귀 위험도 산다. Godot 경로는 파일 단위라 이미 덜하다.

**게임 스켈레톤 템플릿** — 검증된 Canvas 게임 뼈대(루프·입력·상태머신·HUD)를 고정 텍스트로 주면
매번 처음부터 짜지 않아도 된다. 첫 생성 품질에 영향이 커서 별도로 다루는 게 맞다.

**`descope` 액션** — 계약이 애초에 달성 불가능하면 지금은 매 사이클이 같은 자리에서 실패한다.
축소를 허용하면 실패한 런을 작지만 완성된 게임으로 바꿀 수 있다. 다만 두 가지 위험이 있다 —
사람이 승인한 계약을 조용히 줄이는 것, 그리고 **목표를 고칠 수 있는 에이전트는 목표를 고친다**
(버그를 고치는 것보다 요구사항을 지우는 게 항상 쉽다). 먼저 측정이 필요하다: 같은 요구사항이
반복 거부되면 계약 문제, 산발적이면 코드 문제다.

**스프라이트 스타일 일관성** — 각 스프라이트가 독립 프롬프트로 생성돼 화풍이 다를 수 있다.
`clip_vision`/`style_models` 모델 설치가 선행돼야 한다.

## 15. 총괄 감독이 기획을 두 번 하고 있었다

로그가 이상했다. 기획 Agent가 컨셉을 만들었다고 보고한 **다음에** 총괄 감독이 한참을 떠들었다.

감독은 `create_deep_agent`로 만든 서브에이전트 4개짜리 deepagents 감독이었는데, 그 서브에이전트들의
시스템 프롬프트가 **본 파이프라인이 쓰는 바로 그 프롬프트**였다.

```
서브에이전트 idea → IDEA_SYSTEM   ← idea_node 가 쓰는 것과 동일
서브에이전트 art  → ART_SYSTEM    ← art_node 와 동일
서브에이전트 code → CODE_SYSTEM   ← 코드 Agent 와 동일
서브에이전트 qa   → QA_SYSTEM     ← QA 와 동일
```

즉 감독이 `idea`에게 위임하면 **진짜 기획 Agent가 돌았다.** 그리고 `idea_node`가 다시 돌았다.
기획이 최대 12스텝에 걸쳐 두 번 일어나고, 첫 번째 결과는 문단 하나만 남기고 버려졌다. 게다가 그
문단이 말하는 것들 — 범위 통제, 배포 가능성, 안전 — 은 대부분 **이미 코드로 강제되는 것**이다
(`CONTRACT_MAX_ITEMS`, `PLAYABLE FIRST`, 정적 QA 가드레일).

**엔진 불일치도 있었다.** 감독의 code 서브에이전트는 `CODE_SYSTEM`만 알았고 `GODOT_CODE_SYSTEM`은
몰랐다. Godot 런에서도 감독은 "shippable standalone HTML game"을 전제로 제작 지침을 썼고, 기획
Agent는 그 지침에 맞추라는 말을 들었다.

**고친 것**: 감독을 **범위 결정 단일 호출**로 바꿨다. 세 가지만 답한다 — 한 문장 루프, **이번에
만들지 않는 것**, 가장 위험한 부분. 게임을 설계하지 말라고 명시한다. 뒤의 전문가들이 각자 더
잘하는 일이고, 그들에게 필요한 건 두 번째 의견이 아니라 범위다.

뒤에 오는 모든 단계가 못 하는 일이 정확히 **무엇을 뺄지 정하는 것**이다. 플레이 불가 상태로 나온
빌드는 전부 브리프가 함축한 것을 전부 약속해서 생겼다 — 마리오 요청이 가속 곡선·? 블록·코인 잔기·
타이머 보너스·깃발 점수 구간이 되었고, 게임이 시작되기 전에 예산이 떨어졌다. 그 판단은 모델 호출
하나 값을 한다. 게임을 두 번 설계하는 것은 아니다.

그리고 엔진을 알려 준다. Godot 런이면 "project.godot + 씬 + GDScript", HTML5면 "외부 의존성 없는
단일 Canvas 페이지".

스텝·시간 예산은 같이 사라졌다. deepagents가 `recursion_limit=1000`으로 그래프를 만들어 한 번의
`.invoke()`가 수십 분으로 번질 수 있었기 때문에 있던 장치고, **단일 호출에는 가둘 것이 없다.**

기본값은 꺼짐(`DIRECTOR_TIMEOUT_SECONDS=0`)이다. 없어도 모든 단계가 정상 동작하고, 범위 통제는
이제 스키마와 프롬프트가 직접 강제한다. 켜고 싶으면 `.env`에서 `60`으로 바꾸면 된다.
