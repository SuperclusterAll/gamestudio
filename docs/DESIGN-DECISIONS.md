# 설계 판단과 근거

**왜 그렇게 만들었는가.** 대부분 실제로 겪은 실패나 실측에서 나왔고, 그 근거를 같이 남긴다.
시스템 구조는 [ARCHITECTURE.md](ARCHITECTURE.md), 파일별 책임은 [MODULES.md](MODULES.md).

---

## 1. supervisor 패턴을 직접 구현한 이유

`langgraph-supervisor`의 `create_supervisor`를 쓰지 않았다.

**토폴로지는 supervisor 패턴이 맞다.** 허브-스포크, 라우팅 권한 단일화, 모든 워커가 허브로 복귀.
갈리는 지점은 패턴 여부가 아니라 **라우팅을 누가 결정하느냐**다.

`create_supervisor`는 handoff 도구(`transfer_to_<agent>`)로 LLM이 다음 워커를 고른다.
구조상 모든 hop이 모델 호출이다. 실측하면 지금 구조는 이렇다.

| supervisor 진입 | 다음 단계 | 모델 호출 |
|---|---|---|
| 첫 방문 | idea | **1** |
| idea 완료 | design_document | 0 |
| design_document 완료 | approval | 0 |
| approval 승인 | art | 0 |
| art 완료 | code | 0 |
| code 완료 | qa | 0 |
| qa 통과 | package | 0 |
| repair 완료 | qa | 0 |

**8회 방문에 1회.** (+ QA 실패 시 1회) 나머지는 `_NEXT_AFTER[stage]` 딕셔너리 조회다.

바꾸면 얻는 것과 잃는 것:

| | |
|---|---|
| ✅ 토폴로지 | 이미 같음 |
| ✅ QA 실패 시 LLM 판단 | 이미 있음 (`_decide`) |
| ➕ | 결정할 게 없는 hop 6개에 모델 호출 추가 |
| ➖ | 타입 state 계약 상실 — handoff는 공유 `messages`로 넘김 |
| ➖ | `interrupt()` 기반 durable 승인 게이트 |
| ➖ | **코드 수준 예산 강제** |

마지막이 가장 크다. 지금은 rethink가 소진되면 `code`가 선택지에서 **사라진다.**
프롬프트에 "쓰지 마세요"라고 적는 것과 다르다.

측정된 런에서 토큰의 85%가 입력이었다. hop마다 누적 대화 이력을 재전송하는 건 방향이 반대다.

**바꿀 값이 생기는 경우**: 단계 순서 자체가 런타임에 정해져야 할 때. 그때는 `_NEXT_AFTER` 테이블이
성립하지 않으므로 LLM 라우터가 필요해진다.

## 2. 검증은 막을 수 있는 것만 막는다

한 런이 **미해결 31건**을 안고 종료했다. 파고들어 보니 판정 로직에 버그가 있었다.

```python
rejected_ratio = len(rejected) / max(1, len(requirements))
```

`rejected`에는 리뷰어가 **우리가 묻지도 않은 요구사항을 스스로 지어내 거부한 것**까지 들어갔다.
계약을 의역해 자기 표현으로 실패시키면 비율이 1을 넘을 수도 있었고, 정작 실제 계약은 다 충족한
빌드가 차단됐다.

**고친 것**:
- `_verdict()`가 **우리 계약과 실제로 매칭된 것만** 집계
- 리뷰 프롬프트를 "요구사항마다 근거"에서 "**거부한 항목만** 근거"로
- "기타 발견사항"은 계약 위반이 아니라 의견 → 차단하지 않고 5건까지만 기록
- `QA_REJECT_TOLERANCE` 0.34 → 0.5

### 같은 원칙의 다른 적용

**미사용 스프라이트를 차단에서 기록으로 내렸다.** 게임은 돌아간다. 잃은 건 아트 비용이다.
차단하면 rethink 예산을 전부 태우고 **결국 그 지적을 안은 채 배포**한다 — 막지도 못하고 고치지도 못한다.

**키워드 검사는 전부 참고로.** `restart()` 버튼이 있는데 "재시작 없음"으로 읽혀 멀쩡한 게임을
떨어뜨린 적이 있다. 다만 **사실 기반 지적은 항상 표시**한다 — 디스크 위 파일에 대한 사실이지
키워드 추측이 아니다.

## 3. 스트리밍 누적이 2차였다

`gathered = gathered + piece`. 모든 LangChain 예제의 모양이고, 이 길이의 답변에는 함정이다.

`+` 마다 `AIMessageChunk`가 새로 생성되고, 생성할 때마다 `init_tool_calls`가 **누적된 툴 인자
전체를 다시 파싱**한다. 코드 Agent는 게임 한 편을 툴 인자 하나로 쓴다.

실측 (`write_game_file` 호출 모양, 40자 청크):

| 게임 크기 | 청크 | 변경 전 | 변경 후 | |
|---|---|---|---|---|
| 8,000자 | 201 | 0.111s | 0.0003s | 402× |
| 16,000자 | 401 | 0.578s | 0.0009s | 627× |
| 24,000자 | 601 | **1.112s** | **0.0007s** | 1593× |

모델이 말을 다 끝낸 뒤에 우리 루프가 태우던 CPU다. 빌드 1회 + 매 repair, 코드 Agent 턴마다.

`StreamAccumulator`가 조각을 리스트에 append하고 **마지막에 한 번만** 조립한다.
잘린 인자의 partial-JSON 복구는 그대로 유지된다 — 그건 잘림을 정직하게 보고하는 데 필요하다.

> 이 문제를 처음 만난 건 테스트 하나가 **31분 6초** 걸렸을 때다. 파스 불가능한 문자열 400청크로
> 부분 JSON 파서의 최악 경로를 탔다. 고친 뒤 같은 스위트가 8초에 끝난다.

## 4. 검증과 판단을 Haiku로

설계 감사는 **완성된 게임과 배포 사이에 그대로 놓여 있다** — 지연이 끝에서 끝까지 체감되는
유일한 단계다. 그런데 하는 일은 저작이 아니라 판단이다. 읽고 짧은 판정을 낸다.

Sonnet은 검사만 하면 되는 코드에 대해 수천 토큰짜리 에세이를 썼다. Haiku 4.5가 같은 질문에
몇 배 빠르게, 훨씬 싸게 답한다.

**같이 고친 정합성 버그**: 가격표에 Sonnet 4.6밖에 없었다. QA를 Haiku로 옮겼으면 대시보드 비용
추정이 **전체 런에 대해 조용히 `priced: false`** 로 바뀔 뻔했다. 대시보드가 제공하는 모든 모델의
가격을 넣고 테스트로 고정했다.

## 5. 프롬프트 캐싱

측정된 런에서 토큰의 85%가 입력이었는데 캐싱을 전혀 안 쓰고 있었다.

코드 Agent는 매 호출마다 [시스템 프롬프트 + 도구 정의 7개(~2,700토큰) + 누적 대화]를 다시 보낸다.
앞부분은 **한 런 내내 바이트 단위로 동일**하다.

실측 (실제 Bedrock 호출):

| 호출 | 입력 토큰 | 캐시 읽기 |
|---|---|---|
| 1회차 | 5,401 | 0 |
| 2·3회차 | 5,401 | **5,061** |

캐시 읽기는 입력 단가의 1/10이다. 20회 루프면 입력의 약 94%가 캐시가 된다.

**Anthropic 모델에만 적용한다.** Nova는 cachePoint 위치 규칙이 달라 잘못된 조합이 무시가 아니라
**API 거부**로 돌아온다. 비용 최적화가 런을 죽일 수 있으면 안 된다.

비용 추정도 같이 고쳤다. 캐시 읽기를 정가로 세면 **캐싱이 만들어낸 바로 그 상황에서 추정이
틀리고**, 캐싱이 작동하는지도 안 보인다.

## 6. 결정론적 검증은 모델 호출 없이 끝낸다

`write_game_file`이 예전엔 "다음으로 `run_static_qa`를 호출하세요"라고 안내만 했다.
그런데 `static_qa`는 모델 호출이 없고 내용별 캐시까지 된다. **쓰기 시점에 이미 알 수 있는
답을 물어보려고 턴을 하나 쓰는 것**이다.

빌드 루프가 write→qa→repair→qa 구조라 왕복이 두 배가 됐다. 이제 쓰기/수정 결과에 판정이 실려 온다.

Godot의 `run_godot_qa`는 엔진을 실제로 돌려 수십 초가 걸리므로 분리를 유지한다.

같은 이유로 `generate_asset` 도구를 제거했다. 아트 계획을 파일로 저장할 뿐인데 **도구 슬롯과
설명 토큰을 매 호출 차지**했다. 그래프에서 직접 쓴다.

## 7. state에 넣지 않는 것

코드 Agent 전체 대화가 그래프 state에 들어가고 있었는데 **읽는 곳이 한 군데도 없었다.**
에이전트는 매번 자기 payload를 새로 만들고, 대시보드는 `public()`에서 제외한다.

그 안에 `write_game_file` 인자, 즉 게임 전체가 들어 있어 체크포인트마다 재직렬화됐고
rethink마다 누적됐다. 빌드에서 런이 필요로 하는 것은 디스크에 있다.

`trace_notes`도 상한이 없었고 총괄 감독 브리프 전문이 그대로 들어갔다. 요약 + 최근 24개로 제한.

## 8. 승인 게이트의 지속성

`interrupt()` + 체크포인터는 "며칠 뒤 재개"를 위한 구조인데, 실제로는 `InMemorySaver`였다.
**프로세스가 죽으면 대기 중인 승인이 사라진다.** 완성된 게임은 디스크에서 살아남지만 그건
파일이지 실행 상태가 아니다.

SQLite로 바꾸고 검증했다:

```
1) 승인 대기 진입: ('approval',)
2) 재시작 후:      ('approval',)   기획서 제목: 지속성 테스트
```

DB를 못 쓰는 환경에서는 메모리로 조용히 떨어진다 — 영속성은 가질 만하지만 **그것 때문에
실패할 만하지는 않다.**

## 9. 자동 기획이 같은 게임만 만들던 문제

자동 기획으로 3번 돌렸더니 3번 다 별똥별 게임이었고 둘은 제목까지 같았다.

코드 버그가 아니라 **프롬프트가 출력 공간을 붕괴시킨** 것이다.

```
auto 일 때 참조 게임: ''        ← 빈 문자열
슈팅 일 때        : Space Invaders / Galaga / Geometry Wars
```

`GENRE_REFERENCES`가 장르로 키가 잡혀 있어 장르를 안 고르면 **대표작도 안 붙는다.**
자유롭게 들리지만 실은 반대다. 앵커가 사라진 자리에 나머지 제약만 남는다 — 단일 캔버스 파일,
60~120초 세션, 경쟁할 점수 지표, 소극적 플레이 처벌, 검증된 루프 차용. 그 교집합의 "가장 뻔한 답"이
떨어지는 물체 + 콤보 배율이다.

`Run seed`가 이걸 막으라고 있었는데 막을 수가 없었다. **프롬프트 속 헥스 문자열은 샘플링 시드가
아니다.** 모델이 그걸로 다른 설계를 만들 방법이 없다.

**고친 것**: 시드를 해시해 장르 하나를 배정한다. 그러면 시드가 원래 하려던 일을 한다 —
다른 시드는 다른 게임, 같은 시드는 같은 게임. 그리고 배정된 장르의 대표작이 같이 붙는다.

수정 후: 퍼즐(Tetris+2048), 퍼즐(2048 입력), 액션 생존(Vampire Survivors 루프).

### 9-1. 그래도 출력이 6가지였다 — 표 크기가 한계였다

장르 배정은 맞는 수였지만, 표가 **6개 장르 × 3개 게임 = 18개**였다. 자동 기획의 변동 폭이 정확히
6가지였다는 뜻이고, 한 장르 안에서는 늘 같은 대표작 3개로 출발했다.

여기서 "유명 게임을 벡터 DB로 검색해 붙이자"는 안이 나왔지만 **쓰지 않았다**. 자동 기획에는
임베딩할 질의가 없다 — 플레이어가 아무것도 안 썼다는 게 자동 기획의 정의다. 그 상태의 유사도
검색은 검색이 아니라 랜덤 샘플링이고, 그럴 거면 `random`이 더 정확하고 빠르다. 게다가 모델은
Tetris를 이미 안다. 검색이 값을 하는 건 모델이 모를 때 — 사내 문서, 학습 이후 자료다.

**고친 것 셋**:

| | 전 | 후 |
|---|---|---|
| 표 크기 | 6장르 × 3게임 = 18 | **15장르 × 5~7게임 = 87** |
| 장르 안 | 고정된 3개 | 런 시드로 **3개 샘플링** |
| 조합 수 | 6 | 수백 |

시드가 장르뿐 아니라 그 안의 대표작 조합까지 고른다. 같은 시드는 같은 조합을 재현하고, 다른
시드는 같은 장르라도 다른 자리에서 출발한다. 인프라 없이 리터럴 하나로 끝나는 일이다.

### 9-2. 시드가 플레이어를 덮어쓰고 있었다

평가 하네스를 붙이고 나서 실측으로 잡힌 버그다.

```
플레이어가 쓴 요청 : 블록을 회전시켜 빈틈없이 쌓는 게임을 만들어줘
시드가 배정한 장르 : 플랫포머
붙는 참조 게임    : Super Mario Bros / Celeste / Doodle Jump
```

**테트리스를 묘사했는데 마리오가 붙었다.** `자동 기획`은 드롭박스 기본값이라, 장르를 안 건드리고
브리프만 쓰는 흔한 조작이 전부 여기로 떨어진다. 그때 시드가 플레이어의 문장을 덮어썼다.

**고친 것**: 브리프에 사람이 쓴 문장이 있으면 `resolve_auto_genre`는 아무것도 배정하지 않는다.
대신 `infer_genre`가 그 문장을 읽는다 — 이름 댄 게임이 있으면 그것으로 즉시 결정하고(한글 표기
포함, "팩맨"도 잡힌다), 없으면 루프 단어가 **2개 이상** 맞는 장르를 고른다. 하나는 우연이고
("점프"는 슈팅 브리프에도 나온다) 둘은 묘사다. 못 고르겠으면 **아무것도 안 붙인다** — 틀린 행을
붙이는 게 위 버그 자체였으므로, 추측하지 않는 쪽이 낫다.

여기가 이 프로젝트에서 유일하게 "질의가 있는" 지점이지만 역시 벡터 DB를 쓰지 않았다. 후보가
87개인 리터럴에 임베딩 인덱스를 붙이면 동기화 대상과 실행 간 분산이 하나씩 늘 뿐이고, 정확도는
문자열 매칭보다 나을 게 없다.

프롬프트 문구도 갈라놨다. 플레이어 요청이 없으면 대표작은 **고르라는 메뉴**로 들어가고, 요청이
있으면 **참고 자료**로 들어간다 — "요청에 어긋나는 것은 무시하세요". 메뉴로 주면, 테트리스를
요청받은 모델이 목록에서 가장 가까운 게임을 고르는 쪽으로 샌다.

**장기 기억도 추가했다.** 같은 장르 안에서는 여전히 같은 설계로 간다 — 지난번에 뭘 만들었는지
알 방법이 없으니까. 매니페스트에 이미 기록돼 있으므로 **출력 폴더 자체가 기억**이다.
별도 저장소도, 마이그레이션도 없다.

## 10. 사용자 요청이 최우선

"테트리스랑 완전히 똑같은 게임을 만들어줘"에 다른 게임이 나왔다. 프롬프트를 찍어 보니 셋이
동시에 반대로 밀고 있었다.

| 출처 | 지시 |
|---|---|
| 최근 산출물 회피 | "이것들과 **뚜렷하게 다른** 게임을" ← 조건 없이 적용 |
| `IDEA_SYSTEM` | "최대 하나의 변형만 더하라" |
| `IDEA_SYSTEM` | "독립된 **original work**여야 한다" |

첫 번째가 특히 문제다. **다양성은 요청이 없을 때 최적화할 값이지 요청에 맞서 쓸 값이 아니다.**
지난주에 퍼즐을 만들었다는 이유로 "테트리스 만들어줘"에 "다른 걸 만들라"고 답하고 있었다.

`player_requested()`가 사람이 직접 쓴 브리프인지 판별하고, 요청이 있으면 회피를 적용하지 않으며
"위 요청이 다른 모든 지침보다 우선"을 명시한다. `IDEA_SYSTEM` 맨 앞에도 같은 원칙을 두어
시스템 프롬프트와 사용자 프롬프트가 싸우지 않게 했다.

결과: 7종 테트로미노, 회전, 하드드롭, 줄 제거, 레벨별 낙하 속도, 다음 조각 미리보기.

## 11. 아트 — 계획과 생성의 분리

`art` 노드는 그림을 그리지 않는다. 목록만 쓴다. 실제 생성은 code가 한다.

**왜**: art는 코드가 존재하기 전에 컨셉만 보고 계획한다. 코드 Agent는 만들면서 필요를 발견한다.
미리 뽑으면 (1) 틀린 계획에 예산을 태우고, (2) 직렬 대기가 생기고, (3) 무엇보다 **방향을 모른다.**

**예외**: 재수립일 때는 art가 직접 생성한다. 그 시점의 객체는 이미 결정돼 있다 — 검증이 지목했다.
발견할 게 없다. 그리고 코드 Agent 루프 안에서 생성하면 코딩과 경쟁한다.

> 실측된 실패: 한 런이 호출 4개를 스프라이트 생성에 쓰고 **연결할 호출이 남지 않았다.**

파이썬 함수 직접 호출이라 **모델 호출 0회**다. 방향은 `sprites.json`에서 기존 스프라이트의
방향을 읽어 이어받는다 — 재수립 시점엔 게임이 이미 있어 카메라가 정해져 있다.

### 강제 3단

재수립이 목록에 항목을 추가해도 코드 Agent가 건너뛰면 **같은 지적이 다음 사이클에 돌아온다.**
그래서 `required_assets`는 메뉴가 아니라 의무다.

1. 프롬프트에 "MANDATORY ART" 명시
2. 코드 Agent 자기 검증 도구가 통과를 거부 (예산 남았을 때 잡는 자리)
3. 그래프 QA 백스톱 (예산을 다 써서 멈춘 경우)

단, **이미지 생성이 꺼진 런에는 의무를 주지 않는다.** 아무도 만들 수 없는 것을 요구하면
남은 사이클이 전부 고칠 수 없는 지적에 막힌다.

## 12. 스프라이트 배경 제거

ComfyUI의 `RemoveBackground` 노드는 있지만 `background_removal` 모델 폴더가 **비어 있다.**
(익스포트 템플릿과 같은 상황) 그래서 파이썬 쪽에서 잘라낸다 — 장당 **0.8초**, 생성 40초에 비하면 공짜다.

**1차 시도가 실패했다.** "단색 배경"만 요청했더니 모델이 **어두운 배경**을 골랐고, 차체도 어두워서
플러드 필이 차체를 관통했다. 배경색을 모델에 맡기면 안 된다.

**2차도 실패했다.** 크로마키를 요구하고 순수 `#00FF00`과의 거리로 판정했더니, 실측 배경이
`(6,224,10)` · `(22,254,91)` · `(117,212,113)` — 명백히 초록인데 순수 키와는 멀어서 멀쩡한 컷을 버렸다.

**최종**: 판정을 "**초록이 지배적인가**"로, 픽셀 비교는 **모델이 실제로 칠한 배경색** 기준으로.
색 + 연결성 둘 다 본다.

> 중간에 만난 함정: `Image.fromarray`가 **readonly** 이미지를 돌려주고 floodfill의 쓰기가
> 조용히 버려진다. 채워도 `getpixel`이 옛 값을 반환한다. 중간 숫자가 전부 정상이라
> 실제 생성 두 라운드를 태우고서야 찾았다. `.copy()` 한 줄.

**남은 제약**: 외곽선 없이 배경 초록과 바로 맞닿은 초록 피사체는 같이 잘린다. 도구 설명에
"밝은 초록 객체는 요청하지 말 것"을 명시했다.

## 13. Godot 모드

### 웹 익스포트를 전제하지 않는다

`web_nothreads_{debug,release}.zip` 템플릿이 필요한데 Godot은 이걸 **전 플랫폼 묶음(약 1GB)**
으로만 배포한다. 편집기가 있는 머신도 템플릿은 없는 경우가 매우 흔하다.

그래서 **프로젝트가 산출물**이고 웹 빌드는 보너스다. 템플릿이 없으면 그 사실을 정확히 설명하고
`run.bat`으로 실행할 수 있게 한다. 템플릿이 설치되면 코드 수정 없이 웹 빌드가 켜진다.

### `repair`가 없다

`repair`는 게임 전체를 텍스트 한 덩어리로 돌려받는 모델 호출 1회다. HTML에겐 완성품이지만
`project.godot` + 씬 + 스크립트로 이뤄진 프로젝트에겐 무의미하다. 파일을 여러 개 쓸 수 있는
코드 Agent 루프로만 고친다.

부작용: `MAX_RETHINK_CYCLES=1`이면 **실질 재시도가 한 번**이다. HTML은 두 번.

### 엔진이 못 보는 것

엔진은 던져지는 것만 본다. `func _ready(): pass`뿐인 프로젝트는 아무것도 안 던진다 —
임포트되고, 5초 돌고, exit 0이고, **통과로 보고됐다.** 입력도 점수도 승패도 없는데.

`static_project_qa`가 그 자리를 메운다. 특히 `res://` 경로 실재 확인은 엔진이 못 하는 일이다 —
5초 헤드리스 실행은 **그때 지나간 코드 경로만** 건드린다. 입력이 필요한 분기의 `load()`는
절대 안 열리고, 깨진 경로가 플레이어 PC에서 처음 드러난다.

### WASD를 차단하지 않는 이유

웹에서는 진짜 결함이다 — `event.key`가 레이아웃 의존이라 한글 IME에서 W가 'ㅈ'로 온다.
하지만 **Godot의 `physical_keycode`는 레이아웃 독립**이라 그 버그가 성립하지 않는다.
방향키만 쓰는 건 설계 선택이지 고장이 아니다.

## 14. 오탐이 예산을 태운 사례

테트리스 런이 이렇게 끝났다.

```
QA 검증 — 엔진 검증 실패: 생성된 스프라이트를 프로젝트가 참조하지 않습니다:
          block-i.png, block-l.png, block-o.png
총괄 감독 — 수정·재검토 예산을 모두 사용했습니다
QA 검증 — 미해결 1건이 남은 상태로 게임을 배포합니다
```

재현해 보니 **제 검사의 오탐**이었다. 테트리스는 조각을 루프로 다룬다.

```gdscript
func texture_for(kind: String) -> Texture2D:
	return load("res://assets/block-" + kind + ".png")
```

리터럴 `"block-i.png"`가 소스 어디에도 없다. 문자열 일치만 보는 검사는 **스프라이트를 완벽하게
쓰고 있는 게임**을 "참조하지 않음"으로 판정했다. 정상 작성 방식 3종이 모두 오탐이었다.

두 번째 오탐이 겹쳐 있었다. 소스에 남는 조각 `res://assets/block-`을 "존재하지 않는 리소스"로도
잡았다. 파일명이 아니라 경로의 왼쪽 절반인데.

**고친 것**:
- `res://` 경로를 조립하는 코드가 하나라도 있으면 미사용 보고를 **아예 하지 않는다**
- 공통 접두사(`block-`)가 소스에 등장하면 사용 증거로 인정
- 확장자가 없거나 `%{}$*`가 섞인 참조는 리소스 검사에서 제외
- 미사용 아트를 차단에서 **기록으로** (§2)

**교훈**: 읽어서 알 수 없는 것에 대해서는 침묵하는 게 낫다. 틀린 "낭비했습니다"는 rethink 한
바퀴를 태워야 반증된다.

## 15. RAG를 쓰지 않는 이유

검토했고, 이 구조에서는 값을 하는 자리가 없다.

| 필요한 지식 | 판단 |
|---|---|
| Canvas API, GDScript 4 문법 | ❌ 모델 가중치에 있음 |
| 프로젝트 자체 코드 | ❌ 게임 하나가 5~20KB. 통째로 넣어도 되고 부분 읽기도 있음 |
| 과거 만든 게임들 | ⚠️ 이건 RAG가 아니라 **few-shot 템플릿** |
| 최근 산출물 회피 | ✅ 필요하지만 **파일 목록 읽기**로 충분 (§9) |

vector DB가 값을 하려면 사람이 못 고를 규모의 **보유 라이브러리**가 있어야 한다.
이 파이프라인은 자기 아트를 스스로 생성한다. 뒤질 라이브러리가 없다.

> **덧붙임 (§18)**: 이 판단은 *텍스트 지식*에 대해서는 지금도 유효하다. 다만 라이브러리가 없다는 전제가
> 틀렸다 — **런을 돌릴수록 생긴다.** 이 스튜디오가 쓴 이미지 프롬프트가 그것이고, 거기에는 질의도
> 라벨도 있다. §18에서 소재를 바꿔 채택했다.

스프라이트 스타일 일관성도 검색이 아니라 **고정 참조**(IP-Adapter/img2img)의 문제다.
후보가 하나뿐이니 유사도 검색이 개입할 자리가 없다.

## 16. 실패를 숨기지 않는다

전체를 관통하는 원칙이다.

| 상황 | 하는 일 | 하지 않는 일 |
|---|---|---|
| Bedrock 자격증명 없음 | 503으로 거부 | 템플릿 게임으로 대체 |
| Godot 없음 | "건너뛰었습니다" 명시 | 통과로 보고 |
| Node 없음 | JS 검사만 생략 | 빌드 실패 |
| ComfyUI 없음 | Canvas 전용 명시 | 조용히 그림 없이 진행 |
| 익스포트 템플릿 없음 | 이유 설명 + `run.bat` | 실패로 취급 |

| 출력 예산 초과 | "잘렸습니다" + 예산 증액 재시도 | 스키마 위반으로 위장 |

**"조용히 성공한 척"이 이 시스템에서 가장 비싼 실패 모드다.** 승인 게이트의 의미가 사라지고,
사용자가 없는 게임을 있다고 믿게 된다.

## 17. 총괄 감독이 기획을 두 번 하고 있었다

로그가 이상했다. 기획 Agent가 컨셉을 만들었다고 보고한 **다음에** 총괄 감독이 한참을 떠들었다.

감독은 `create_deep_agent`로 만든 서브에이전트 4개짜리 deepagents 감독이었는데, 그 서브에이전트들의
시스템 프롬프트가 **본 파이프라인이 쓰는 바로 그 프롬프트**였다.

```
서브에이전트 idea → IDEA_SYSTEM   ← idea_node 가 쓰는 것과 동일
서브에이전트 art  → ART_SYSTEM    ← art_node 와 동일
서브에이전트 code → CODE_SYSTEM   ← 코드 Agent 와 동일
서브에이전트 qa   → QA_SYSTEM     ← QA 와 동일
```

즉 감독이 `idea`에게 위임하면 **진짜 기획 Agent가 돌았다.** 그리고 `idea_node`가 다시 돌았다.
기획이 최대 12스텝에 걸쳐 두 번 일어나고, 첫 번째 결과는 문단 하나만 남기고 버려졌다. 게다가 그
문단이 말하는 것들 — 범위 통제, 배포 가능성, 안전 — 은 대부분 **이미 코드로 강제되는 것**이다
(`CONTRACT_MAX_ITEMS`, `PLAYABLE FIRST`, 정적 QA 가드레일).

**엔진 불일치도 있었다.** 감독의 code 서브에이전트는 `CODE_SYSTEM`만 알았고 `GODOT_CODE_SYSTEM`은
몰랐다. Godot 런에서도 감독은 "shippable standalone HTML game"을 전제로 제작 지침을 썼고, 기획
Agent는 그 지침에 맞추라는 말을 들었다.

**고친 것**: 감독을 **범위 결정 단일 호출**로 바꿨다. 세 가지만 답한다 — 한 문장 루프, **이번에
만들지 않는 것**, 가장 위험한 부분. 게임을 설계하지 말라고 명시한다. 뒤의 전문가들이 각자 더
잘하는 일이고, 그들에게 필요한 건 두 번째 의견이 아니라 범위다.

뒤에 오는 모든 단계가 못 하는 일이 정확히 **무엇을 뺄지 정하는 것**이다. 플레이 불가 상태로 나온
빌드는 전부 브리프가 함축한 것을 전부 약속해서 생겼다 — 마리오 요청이 가속 곡선·? 블록·코인 잔기·
타이머 보너스·깃발 점수 구간이 되었고, 게임이 시작되기 전에 예산이 떨어졌다. 그 판단은 모델 호출
하나 값을 한다. 게임을 두 번 설계하는 것은 아니다.

그리고 엔진을 알려 준다. Godot 런이면 "project.godot + 씬 + GDScript", HTML5면 "외부 의존성 없는
단일 Canvas 페이지".

스텝·시간 예산은 같이 사라졌다. deepagents가 `recursion_limit=1000`으로 그래프를 만들어 한 번의
`.invoke()`가 수십 분으로 번질 수 있었기 때문에 있던 장치고, **단일 호출에는 가둘 것이 없다.**

기본값은 꺼짐(`DIRECTOR_TIMEOUT_SECONDS=0`)이다. 없어도 모든 단계가 정상 동작하고, 범위 통제는
이제 스키마와 프롬프트가 직접 강제한다. 켜고 싶으면 `.env`에서 `60`으로 바꾸면 된다.

## 18. 벡터 DB는 기각했다가, 소재를 바꿔 채택했다

§9-1에서 "유명 게임을 벡터 DB로 검색해 붙이자"를 기각했다. 자동 기획에는 임베딩할 질의가 없고, 모델은
Tetris를 이미 알고, 진짜 한계는 표 크기였기 때문이다. 그 판단은 지금도 유효하다.

그런데 **이미지 쪽에는 진짜 공백이 있었다.** 아트 디렉터는 `image_prompt`를 **아무 시각적 근거 없이 산문으로**
쓴다. 팔레트·타일 크기·작은 화면 가독성 — 스크린샷 한 장이면 즉시 잡히는 것들이고, 스무 번째 런이 첫
번째 런만큼이나 맹목적으로 프롬프트를 썼다.

**소재를 바꿨다.** 남의 스크린샷이 아니라 **이 스튜디오가 쓴 프롬프트**를 쌓는다.

| | 유명 게임 이미지 RAG | 자기 프롬프트 RAG |
|---|---|---|
| 저작권 | 남의 아트 파생 | 자기 프롬프트·자기 이미지 |
| GPU | CLIP + IPAdapter가 RTX 2060에 부담 | 텍스트 임베딩만 |
| 전이되는 것 | 픽셀 | **말** — 같은 프롬프트도 다른 그림이 나온다 |
| 질의 | 없음 | `visual_direction` — 있다 |
| 라벨 | 없음 | 사람의 좋음/별로 — **결과로 배운다** |

전자가 넘는 선은 이 프로젝트가 **이미 코드에 적어 둔 것**이다. `IDEA_SYSTEM`은 특정 게임을 그대로 재현해도
된다고 하면서 이렇게 끝난다: *"제목·캐릭터·아트만 직접 가져오지 않으면 됩니다."* 메커닉은 저작권 대상이
아니고 아트는 대상이다. `GENRE_REFERENCES`가 87개 게임의 **루프만** 적고 그림을 한 장도 안 쓰는 것이 우연이
아닌 이유다.

### 공짜 라벨이 먼저 돈다

`removed_share`(배경 제거에서 잘려 나간 비율)가 이미 기록되고 있었다. 실측하니 80장 중 **17장(21%)이 한 변
120px 미만**이었다 — 1024에서 생성했는데 그만큼만 남았다는 건 모델이 큰 여백 안에 캐릭터를 작게 그렸다는
뜻이고, 확대하면 뭉갠다.

그래서 **사람에게 묻기 전에** 그런 것들을 먼저 거른다. *"작게 나왔다"* 는 이미 기록 중인 기하학에 보이지만
*"보기 좋다"* 는 안 보인다. 자동 판정이 **실패만** 붙이고 좋음은 사람 몫인 이유다.

### 역할은 렌더 방식이 아니다

기존 `kind`는 `sprite`/`backdrop` 두 값뿐이고 **어떻게 자를지**만 정한다. 무엇인지는 파일 이름에만 있었다
(`enemy-fast.png`, `bullet-player.png`) — 사람 눈에는 보이지만 **조회할 수 있는 필드가 아니다.**

`role` 9종을 고정 목록으로 추가했다. *"슈팅 장르에서 좋게 평가된 **적** 프롬프트"* 조회는 모든 적이 자기를
적이라고 부르기로 합의해야 성립하고, 자유 텍스트로는 성립하지 않는다.

### 재개발하면 평가셋이 다시 만들어진다

재개발은 같은 폴더·같은 런 id로 돈다. 그래서 재생성된 스프라이트는 같은 행을 덮어쓰고 **판정이
초기화된다** — 맞다. 새 이미지이고, 옛 판정은 그것을 설명하지 않으며, 다시 물어야 한다.

평가셋은 **디스크가 정한다.** 재개발이 어떤 스프라이트는 다시 뽑고 어떤 것은 버리고 어떤 것은 새로
만드는데, 두 빌드 전의 게임을 설명하는 평가셋은 가치가 없다. 리뷰어가 **게임에 더 이상 없는 이미지를
판정**하게 되니까.

다만 **사람이 "좋음"이라 한 프롬프트는 덮어쓰기 전에 보관한다.** 그것이 이 스토어가 존재하는 이유
그 자체이고, 스프라이트를 다시 뽑았다고 버리면 모으려던 것을 버리는 셈이다. 보관본은 평가 패널에는 안
나오고(설명하는 이미지가 없으니) 조회에는 잡힌다(프롬프트는 여전히 통했으니).

## 19. 저장소를 산출물 폴더에서 꺼냈다

체크포인트 DB와 벡터 스토어가 `GAME_OUTPUT_DIR`에 있었다. 사람이 **게임을 찾으러 들어가는 폴더**에 249MB
SQLite 파일과 벡터 DB가 앉아 있었다는 뜻이다.

둘 다 배포물이 아니다. 이 프로세스 말고는 아무도 안 열고, **읽는 코드 옆에 있어야 한다.** `data/`로 옮기고
git이 무시하게 했다. 첫 실행 때 스스로 만들어지므로 다른 PC에서 클론해도 설정 단계가 없다.

**옮기는 것도 조심해야 했다.** 승인 대기 5건이 살아 있었고 대시보드가 파일을 잡고 있었다. SQLite 온라인
백업 API로 옮겼다 — 다른 프로세스가 쓰는 중에도 일관된 스냅샷을 보장하는 방식이다.

그리고 **정리 루틴을 붙였다.** LangGraph는 super-step마다 상태를 통째로 직렬화한다(증분이 아니다). 한 런이
229개 체크포인트 × 평균 62KB = 10~18MB이고, 아무것도 지우지 않았다.

정리 판정은 `graph.get_state().next`가 비었는지 하나다. **승인 대기도 중간에 죽은 런도 `next`가 비지
않으므로**, 왜 멈췄는지 알 필요 없이 같은 검사로 둘 다 보호된다 — 그게 이 방식이 안전한 이유다.

만들다가 두 가지를 잡았다. `saver.list(None)`이 체크포인트 3,826개를 **전부 역직렬화**해서 스레드 37개
이름을 알아냈다(90초). SQL 한 줄로 바꿔 0.0초가 됐고, 이건 테스트만이 아니라 **매 대시보드 시작이 그만큼
걸렸을** 문제였다. 그리고 `TestClient(app)`가 lifespan을 돌리면서 **개발자의 진짜 DB를 정리할 뻔했다** —
보존 기간이 막았지만, 테스트가 남의 승인 대기를 지우는 건 일어나면 안 되는 일이다.

## 20. 한도가 차면 같은 모델의 다른 문으로 간다 — 단, 그게 통하는 한도일 때만

강의용 단체 약정 계정이라 **오후에 한도가 찬다.** 하필 코드 Agent가 한 런의 모델 호출 대부분을 쓰는
단계라서, 40번째에 막히면 **반쯤 쓰인 게임 파일이 디스크에 남은 채로** 런이 끝났다.

Bedrock은 인퍼런스 프로파일마다 라우팅이 다르다. `global.anthropic.claude-sonnet-4-6`이 분당 스로틀에
걸렸다고 `us.`도 같으리란 법은 없다. 그래서 막히면 옆문으로 같은 질문을 하게 했다 — 구조화 출력은
`_structured`가 프로파일 목록을 걸어가고, 코드 Agent는 `ModelFallbackMiddleware`가 같은 일을 한다.

**다른 모델은 안 쓴다.** 절반은 Sonnet이 쓰고 절반은 더 싼 모델이 쓴 게임보다, 멈추고 이유를 말하는 런이
낫다. 움직이는 건 프로파일 접두사뿐이다. 같은 이유로 `eu.`/`apac.`도 뺐다 — 권한이 없어서 한도 오류가
**원인에서 더 먼** 권한 오류로 바뀐다.

### 그리고 실제로 실패한 다음에 알게 된 것

붙이고 나서 아트 기획이 정확히 이 지점에서 죽었다. 로그는 `us.`로 넘어간다고 찍고, 거기서 끝났다.
계정에 직접 물어보니 전제가 틀려 있었다.

| 모델 | 상태 |
|---|---|
| `global.` Sonnet 4.6 | `Too many tokens per day` |
| `us.` Sonnet 4.6 | `Too many tokens per day` |
| `global.` Sonnet 4.5 | `Too many tokens per day` |
| Haiku 4.5 (양쪽 프로파일) | 정상 |

**같은 1분 안의 결과다.** 일일 토큰 한도는 프로파일별이 아니라 **모델 계열 단위로 계정 전체가 나눠 쓴다.**
프로파일을 바꿔도 이미 빈 통을 다시 여는 것이라 처음부터 갈 곳이 없다. 게다가 실패 메시지가 **마지막으로
시도한 프로파일 이름**을 달고 나와서, 로그를 읽는 사람을 아무 상관 없는 `us.` 쪽으로 보낸다 — 이 기능이
막으려던 바로 그 실패다.

그래서 **두 스로틀을 갈라서 다룬다.** 분당 스로틀에는 원래대로 옆문을 연다. `tokens per day`가 보이면
프로파일 순회를 **아예 건너뛴다** — 같은 통을 나눠 쓰니 호출 세 번을 더 태울 이유가 없다.

그리고 거기서 **한 발 더 간다. 일일 한도일 때만 다른 모델(Haiku 4.5)로 넘어간다.** 위에서 "다른 모델은
안 쓴다"고 해놓고 쓰는 것이므로, 왜 뒤집었는지가 중요하다 — 일일 한도에서 선택지는 *"일관된 게임이냐
섞인 게임이냐"*가 아니라 *"섞인 게임이냐 내일까지 게임 없음이냐"*다. 강의용 계정에서는 후자가 하루를
통째로 날린다.

대신 **조용히는 안 한다.** 전환은 런 로그에 그대로 찍히고, 호출을 모델별로 세서
`usage.calls_by_model`로 매니페스트에 남긴다. 그게 없으면 이 게임은 다른 Sonnet 런과 똑같아 보이고,
차이는 나중에 *"이건 왜 좀 별로지"*로만 드러난다 — 원인에 연결할 방법 없이. 기준선과 비교하는 중이라면
`BEDROCK_DAILY_CAP_MODEL_ID`를 비워서 끄면 되고, 그러면 런이 멈춘다.

남는 교훈은 기능 자체보다 이쪽이다 — **어떤 오류인지 안다고 생각하고 대책을 세웠는데, 계정에 물어보니
같은 예외 하나에 성질이 정반대인 두 가지가 들어 있었다.** 재현해보기 전까지는 대책이 맞는지 알 수 없었다.

**만들면서 잡은 게 둘 더 있다.** `except Exception`을 `except ValidationError` **위에** 뒀더니 스키마 위반도
Exception이라 한도 오류로 잡혔고, `_structured`가 존재하는 이유인 스키마 재시도가 조용히 죽었다. 그리고
프로파일 전환이 **재시도 횟수를 한 번 먹고 있었다** — 한도 오류는 답 내용에 대해 아무 말도 하지 않으므로
운 나쁜 스로틀 하나가 검증 재시도를 깎으면 안 된다. 횟수는 이제 스키마 실패만 센다.

## 21. 애니메이션 프레임은 "한 장에 다 그리기"로 풀었다

걷는 모습을 프레임마다 따로 요청하면 **매번 다른 캐릭터가 왔다.** 화풍이 바뀌고, 무늬가 생기고,
좌우가 뒤집히고, 배경이 붙은 채로 오기도 했다.

**이미지 모델이 내놓는 수단을 전부 실측했다.**

| 방식 | 캐릭터 동일성 | facing | 포즈 변화 |
|---|---|---|---|
| `IMAGE_VARIATION` 0.9 / **1.0** | ✗ 다른 고양이 | ✗ 뒤집힘 | ✓ |
| `INPAINTING` (다리만 마스크) | ✗ 외곽선 소실·눈 색 변경 | ✓ | △ |
| `CANNY_EDGE` / `SEGMENTATION` 0.3 | ✓ | ✓ | ✗ **잠김** |
| **1회 생성 시트** | **✓** | **✓** | **✓** |

구조적인 이유가 있다 — **정체성을 지키는 방식은 포즈도 같이 잠그고, 포즈를 푸는 방식은 정체성도 같이
놓는다.** 둘을 분리하는 장치(IP-Adapter 류)가 노출된 태스크에 없다. `controlStrength`를 0.3까지
낮춰도 엣지맵이 프롬프트를 이겼다.

그래서 **한 번의 생성 안에 전부 그린다.** 한 장 안에서는 화풍이 드리프트할 수 없으니 일관성이 지시가
아니라 구조로 보장된다. 덤으로 싸다 — 시트 66.7초 대 단일 31.5초×4=126초, 그리고 코드 Agent 호출이
프레임당 1회가 아니라 **총 1회**다. 이미지가 게임 코드와 같은 호출 예산을 쓰므로 뒤쪽이 더 크다.

### 자르면서 알게 된 것

**균등 셀로 나누면 안 된다.** 모델은 균등 간격으로 안 그린다 — 1536px 시트의 실제 위치가
99-376, 496-772, 876-1081, 1189-1433이었고 384px 균등 셀은 두 번째 프레임을 반으로 잘랐다.

**"한 줄"을 요청해도 2행으로 그릴 때가 있다.** 열만 보고 잘랐더니 한 프레임에 고양이가 세로로 두 마리씩
들어갔고, 모든 프레임이 같은 쌍을 담으니 실루엣이 **99% 일치**했다. 지표만 보면 역대 최고였다 —
*움직이지 않는* 애니메이션인데. 프레임을 늘어놓고 눈으로 보기 전까지 몰랐다.

**정렬 기준도 수치가 거짓말을 했다.** 프레임 간격 분산은 bbox 중심을 선호했는데(27.8px 대 37.4px),
정렬한 프레임을 겹쳐보니 정반대였다 — bbox에서는 머리가 흩어지고, 무게중심에서는 몸통이 하나로 맞고
다리와 꼬리만 갈라졌다. bbox는 **가장 멀리 뻗은 팔다리**가 결정하는데 걷기에서 그건 움직이라고 있는
부위다. 그리고 무게중심으로 옮기면 캔버스 폭을 bbox 기준으로 잡은 게 모자라 프레임이 잘렸다 —
테스트가 잡았다.

### 정직하게 남긴 한계

시트는 **일관성은** 확실히 주지만 **움직임은** 그렇지 않다. 같은 프롬프트가 시드에 따라 진짜 걷기(13.9%)와
같은 그림 세 장(0.8%)을 모두 낸다. 문구를 세 가지로 바꿔 시드 2개씩 재봤지만 6번 중 5번이 2% 미만이었다 —
**요청의 문제가 아니라 생성의 성질이다.**

그래서 `pose_spread()`로 재고, 5% 미만이면 다른 시드로 한 번 더 뽑고(모델 호출 0회, ComfyUI 시간만 든다),
그래도 안 되면 **경고를 붙여 돌려준다.** 걷는 줄 알고 같은 그림을 세 장 깔면 캐릭터가 다리를 안 움직이고
미끄러지는데, 그건 파이프라인 반대쪽 끝에서 게임 버그로 보인다.

### IP-Adapter는 안 갔다

같은 문제를 정면으로 푸는 방법이지만 이 머신에서는 안 된다. `custom_nodes`가 비어 있고, 설치된 모델은
`z_image_turbo_bf16` UNET 하나뿐이다(SD/SDXL 체크포인트 없음). IP-Adapter 가중치는 UNet 크로스어텐션
형태에 묶여서 Z-Image에는 안 맞는다. 쓰려면 약 10GB를 받고 Z-Image Turbo를 버려야 하는데, **VRAM
6GB(RTX 2060)가 병목**이라 지금 31.5초가 몇 배로 늘어난다. 시트 기법이 이미 해결한 문제다.

## 22. 애니메이션을 10건으로 재봤다 — 그리고 대부분의 결함은 내 프롬프트였다

§21에서 시트 기법을 붙인 뒤, 케이스 10개(사람·동물·로봇·슬라임 × 걷기·달리기·공격·점프·대기)를
실제 도구 경로로 돌렸다. 회차마다 고치고 다시 돌렸다.

| 항목 | 1차 | 2차 | 최종 |
|---|---|---|---|
| 크로마키 성공 | 10/10 | 10/10 | **10/10** |
| 공·소품 안 붙음 | 10/10 | 10/10 | **10/10** |
| 머리 있음 | 10/10 | 10/10 | **10/10** |
| 서로 다른 포즈 ≥3 | 5/10 | 8/10 | **8/10** |

**세 결함은 전부 내가 만든 것이었다.**

**① 공이 캐릭터에 붙었다.** 한 장에 여러 캐릭터를 그리려고 네거티브에서 `multiple objects`를 뺐는데,
그게 **다른 물체 금지까지** 같이 떼어냈다. 두 번째 *캐릭터* 금지만 풀었어야 했다.

**② 머리가 사라졌다.** 포즈를 프레임별로 지정하면서 `leg`·`arm`을 네 번씩 반복했더니 요청의 거의 모든
단어가 팔다리를 가리켰고, 모델은 팔다리만 그렸다. `everything else identical`은 이미지에 머리를 넣어주지
않는다 — **`head`라고 써야** 넣어준다.

**③ 배경이 흰색이었다.** 프롬프트가 1445자인데 전송 직전 1200자로 잘렸고, 그린스크린 지시가 1388자
지점이라 **모델에 도달조차 못 했다.** 파이프라인이 *의존하는* 지시(배경·배치·방향)를 앞으로 옮기고
한도를 올렸다. 잘림은 조용하고 **꼬리를 자르므로**, 꼬리에 필수 지시를 두면 안 된다.

### 몸에 맞지 않는 지시는 잡음이다

포즈 목록이 사람 기준뿐이라 고양이에게 *"the RIGHT **arm** swung forward, the **heel** down"*을 보내고
있었다. 없는 부위를 네 프레임 내내 지시하면 모델에게 **바꿀 거리가 없고**, 같은 그림이 네 번 나온다.

그런데 고쳐놓고 보니 **모델은 게임 속 고양이를 두 발로 세워 그린다.** 종 이름만으로 네발로 분류하면
그림과 어긋난다. 그래서 `on all fours`처럼 **명시할 때**, 또는 말·사슴처럼 아무도 세워 그리지 않는
동물일 때만 네발 어휘를 쓴다.

**그리고 아무 말도 안 하는 것이 최악이었다.** 다리 없는 슬라임에서 (틀린) 다리 지시를 지웠더니 포즈가
**4개에서 1개로** 떨어졌다. 틀린 지시라도 변화를 만들고 있었던 것이다. 다리가 없는 것은 걷지 않고
**변형한다** — 눌리고, 늘어나고, 기운다. 그 어휘를 따로 줬더니 4개로 돌아왔다.

### 측정 도구도 두 번 틀렸다

**시드가 재현되지 않았다.** `hash(tag)`로 잡았는데 파이썬 문자열 해시는 프로세스마다 다르다. 같은
케이스가 한 번은 2개, 다음엔 3개였다 — **비교가 안 되는 벤치마크**였다. SHA-256으로 고정하고 나서야
회차 비교가 의미를 가졌다. (생성 자체는 같은 시드에서 바이트까지 동일하다. 확인했다.)

**"머리 있음" 검사를 슬라임에도 적용했다.** 사람 체형 기하에 기댄 검사라 둥근 것은 무조건 실패한다.
그림이 아니라 측정이 틀린 것이었다.

### 남은 것

포즈 다양성은 회차마다 흔들린다. cat은 네 회차 내내 2개였다. 다만 **부족하면 중복을 버리고 경고를
붙이므로**, 걷는 줄 알았던 정지화가 게임에 들어가지는 않는다. 그리고 3차의 knight 실패 1건은 현재
코드로 재현되지 않는다 — 원인을 모르므로 지어내지 않고 기록만 남긴다.

## 23. 배경이 남는데 아무도 말하지 않았다

캐릭터에 배경이 붙어 나온다는 지적을 받고 실제 자산을 전수로 재봤다.

| 자산 | 크기 | 불투명 | 제거율 |
|---|---|---|---|
| boss-slime.png | 1024x1024 | **100%** | **0%** |
| goal.png | 930x529 | 92% | 56% |
| mushroom.png | 1024x1024 | 55% | 44% |

`keyed_out()`이 **가장 심한 경우에 침묵**하고 있었다.

```python
if entry.get("kind") == "backdrop" or not entry.get("transparent"):
    return ""          # ← 배경이 100% 그대로인 경우가 여기로 빠진다
```

부분 실패(>90% 불투명)에는 "다시 생성하세요"라고 하면서, **제거가 아예 거부된 경우**에는 판정할 투명도가
없다는 이유로 조용히 통과시켰다. boss-slime은 장면이 통째로 구워진 1024x1024 사각형으로 납품됐고
런 어디에도 그 말이 없었다.

**두 번째 유형은 아예 보지 못하고 있었다.** 잘라낸 스프라이트는 **항상 캔버스보다 작다** — 트림이 그림에
맞춰 줄이기 때문이다. 결과가 원본 캔버스와 같은 크기라면 **가장자리까지 불투명**하다는 뜻이고, 그건
장면 조각이 살아남았다는 신호다. mushroom이 55%로 기존 90% 기준을 통과하면서 배경을 안고 있었다.

### 프롬프트 스킬은 답이 아니었다

"프롬프팅을 더 잘해야 하나, 스킬이라도 써야 하나"를 검토하면서 **기존 스프라이트 프롬프트 73개를 전수
검사**했다. `background`·`forest`·`standing on` 같은 장면 단어를 포함한 것이 **0개**였다. 실패한
boss-slime의 요청도 *"뿔 두 개 달린 붉은 대형 슬라임, 크고 둥근 몸통, 성난 눈매"* — 도구가 요구하는
그대로다.

**에이전트의 표현은 문제가 아니었다.** 프롬프트를 다듬는 LLM 호출을 붙였어도 고칠 대상이 없었고, 모델
호출과 지연만 늘었을 것이다.

그래서 **도구가 스스로 다른 시드로 다시 뽑는다.** 에이전트에게 되묻는 것은 모델 호출 1회와 왕복을 쓰고
**같은 요청으로 돌아온다**(요청이 이미 옳으므로). 재추첨은 GPU 시간만 들고, 그 시간에는 §24의 예산이
있다. 두 번까지만 하고 그 뒤에는 Canvas로 넘긴다 — 두 번 실패한 피사체에 세 번째 1분을 쓰는 것보다
게임을 끝내는 게 낫다.

### 장수 예산은 잘못된 것을 재고 있었다

이미지 예산이 **PNG 장수**였는데, 로컬 ComfyUI라 청구되는 것이 없다. 아낄 이유가 없는 것을 아끼게 만들고,
호출마다 `[9/14 of this run's image budget, 5 left]`라고 알려주며 그러라고 시켰다. 요청의 실제 비용은
**시간**이다. 장수는 폭주 방지용 상한으로만 남기고, 에이전트에게는 시계를 보여준다 —
`[이미지 생성 320초 / 600초]`.

## 24. 초록 캐릭터에는 매젠타 스크린을 쓴다

그린스크린 위의 초록 피사체는 배경과 함께 잘려나간다. 이건 한계로 **문서에 적어두고 호출자에게
떠넘기고 있었다** — 도구 설명에 *"밝은 초록 물체는 요청하지 마세요"*라고.

그런데 2D 게임의 몬스터 도감은 대체로 초록이다. 슬라임·좀비·개구리·고블린. 가드가 **가장 필요한
곳에서 지고 있었던 셈**이다.

매젠타가 표준 제2 키인 이유가 이거다 — 초록 피사체 안에 매젠타 근처 색이 없다. 피사체 묘사가 초록을
암시하면 배경을 매젠타로 요청한다. 실측으로 확인했다: 형광 초록 슬라임과 초록 좀비 둘 다 구멍 없이
52% 불투명으로 잘렸다.

**잘라내는 쪽은 어느 키를 요청했는지 묻지 않는다.** 모델이 지시를 무시하고 초록을 칠할 수도 있으므로,
`_backdrop_colour`는 **실제로 칠해진 색**을 읽고 둘 다 받아들인다. 판정은 거리가 아니라 **지배도**다 —
실측 그린스크린이 (6,224,10), (22,254,91), (117,212,113)로 순수 키 근처에 온 적이 한 번도 없다.
매젠타도 같은 방식이되 **두 채널이 동시에 지배적**이라는 점만 다르다.

아이디어는 [jay6697117/game-skills](https://github.com/jay6697117/game-skills)에서 왔다. 다른 이미지
백엔드를 겨냥하는 스킬이지만 *"#ff00ff (magenta) if character uses green"* 이라는 같은 제약을 반대편에서
풀고 있었다. **저장소를 편입시키지는 않았다** — 백엔드가 다르고, 나머지 규칙은 이 프로젝트가 실측으로
이미 도달한 것들이다.

### 캔버스도 같이 줄였다

에이전트가 스프라이트를 1024x1024로 요청하고 있었다. 512x512의 **4배 픽셀이고 시간도 약 4배**인데,
화면에서는 64px로 그려진다. 10분짜리 이미지 예산을 아무도 볼 수 없는 디테일에 쓰고 있었다. 게다가
캔버스가 클수록 모델이 **장면을 채워 넣을 여지**도 커진다 — 잘라내기가 잡으려는 바로 그 실패다.

스프라이트는 512, 배경은 1024로 **상한을 둔다**. 에이전트는 캔버스 하나가 얼마인지 알 방법이 없으므로
요청을 따르지 않고 자른다.

## 25. cfg 2에서 1로 — 모델이 훈련된 대로

워크플로가 `cfg=2`로 저장돼 있었다. Z-Image Turbo 모델 카드는 **"Guidance should be 0 for the Turbo
models"**라고 하고, ComfyUI 쪽 안내는 **cfg 1, 네거티브 프롬프트 없음**이라고 한다. 증류 모델이라
classifier-free guidance가 훈련된 동작이 아니기 때문이다.

같은 프롬프트·같은 시드로 세 대상 두 번씩 쟀다.

| | 평균 시간 | 크로마키 |
|---|---|---|
| **cfg 1.0** | **14.4초** | 6/6 |
| cfg 2.0 | 24.8초 | 5/6 |

**42% 빠르고 더 나빠지지도 않았다.** cfg 1에서는 스텝당 순전파가 2회에서 1회로 줄기 때문이다.

### 대가: 네거티브가 아무 일도 하지 않는다

guidance가 꺼지면 네거티브 브랜치가 벗어날 대상이 없다. **네거티브 프롬프트는 그냥 무력해진다.**
1,100자를 적어둬도 읽히지 않는다.

그래서 파이프라인이 **의존하는** 것은 전부 긍정 프롬프트로 옮겼다. 마침 §22~24에서 이미 대부분
옮겨져 있었다 — 턴어라운드 금지, 머리 보존, 다른 물체 금지, 옷 색 유지가 전부 긍정문으로 다시 쓰여
있었다. 남은 둘만 옮기면 됐고, 둘 다 **금지가 아니라 지시로** 바꿔야 했다:

- *"가리키지 마라"* → **"팔을 몸 옆에 붙이고"**
- *"반짝임 금지"* → **"피사체 주위에 떠 있는 것 없이"**

디퓨전 모델에게 "하지 마라"는 약하고 "이렇게 그려라"는 강하다. §22에서 배운 것과 같다 —
`everything else identical`은 이미지에 머리를 넣어주지 않고 `head`라고 써야 넣어준다.

네거티브 목록 자체는 지웠다가 다시 쓸 일이 없도록 남겨뒀다. cfg를 올리는 사람이 있으면 그때 살아난다.

## 26. 검수자가 읽을 수 없는 것을 요구사항으로 받고 있었다

*"QA는 도대체 뭘 하는 거지"* 라는 물음에서 시작했다. 납품된 게임 13개를 열어보니 **전부 `pass`**,
미충족은 최대 3/18(17%)이었다. 차단 임계는 50%라 근처도 안 간다. **관대해서가 아니었다.**

무엇을 요구사항으로 받고 있었는지가 문제였다.

> *"60~90초 구간에서 가만히 서서 물방울을 쏘지 않으면 30초 이내에 몬스터 6마리에 둘러싸여 목숨을
> 모두 잃고 게임 오버가 되는 것이 **확인된다**"*

> *"포획된 물방울을 5초 기다리면 몬스터가 나오는 것이 **육안으로 확인된다**"*

**아무도 확인하지 않는다.** 설계 감사는 소스를 읽고, 그 프롬프트에는 *"절대 게임을 실행했다고 주장하지
마라"*고 적혀 있다 — 실행이 불가능하니 정직한 지시다. 그러니 관찰형 기준은 **확인할 수도 반증할 수도
없고**, 반증 불가능한 기준은 언제나 통과한다. 16개 요구사항, 16개 통과. 그 게임의 걷기 애니메이션은
중간에 캐릭터가 돌아서 있었다.

### 원인은 빈 필드였다

```python
acceptance_tests: list[ContractItem] = Field(min_length=3, max_length=CONTRACT_MAX_ITEMS)
```

**설명이 한 줄도 없었다.** 다른 필드와 달리 `description`이 비어서, 기획 모델이 형식을 스스로 정하고
가장 자연스러운 것 — 플레이어가 보는 것 — 을 골랐다.

### 설명을 붙이고, 스키마로 강제했다

설명은 조언이고, **조언에 기댄 결과가 방금 그것**이다. 그래서 `field_validator`로 막는다. 계약의 개수·
길이 상한을 프롬프트로 부탁하지 않고 스키마로 거는 것과 같은 이유다. 어기면 검증 오류가 나고,
`_structured`가 불평을 붙여 다시 요청하며, 빌드에 도달하는 계획은 검수자가 실제로 판정할 수 있는 것이 된다.

**의도적으로 좁다.** `"화면에 표시된다"`는 통과한다 — 그리기 호출은 소스에 있고, 화면 얘기를 전부
막으면 게임 계약의 대부분이 사라진다. 막는 것은 **누군가 봤다는 주장** 하나뿐이다.

검수자 쪽에도 나머지 절반을 넣었다. *"네가 받는 요구사항은 전부 이 소스를 읽어서 판정할 수 있다. 판단이
안 선다고 통과시키지 마라."* 이게 없으면 제약이 무의미해진다.

### 이걸로 고쳐지지 않는 것

**깨진 게임을 더 잘 찾아주지는 않는다.** 여전히 아무도 실행하지 않는다. 충돌이 20px 어긋났거나, 첫
프레임에 터지거나, 플레이어가 벽 속에서 시작하는 것은 돌려봐야 안다.

버는 것은 둘이다. **통과가 의미를 갖는다** — 반증 가능한 기준은 근거를 대고 반려할 수 있다. 그리고
**기획이 구체적으로 나온다** — 숫자와 상태 전이로 적게 되니, 그 자체가 코드 Agent에게 더 나은 사양이다.

## 27. 한 런이 그림에 갇히지 않게

PNG 장수가 유일한 이미지 예산이었는데, 그건 **얼마나 오래 묶여 있는지**를 재지 못한다. 실측: 스프라이트
한 장 31초, 애니메이션 시트 58초(최대 166초). 같은 "14장"이 4분일 수도 15분일 수도 있고, 재추첨이 돌면
두 배가 된다. 그동안 코드 Agent는 아무것도 못 쓴 채 대기한다.

그래서 **런당 이미지 시간 예산(기본 600초)**을 뒀다. 다 쓰면 실패가 아니라 *"남은 객체는 Canvas 도형으로
그리세요"*다 — 아트 계획은 원래 Canvas 우선이고 래스터는 개선이다. 재추첨도 시간이 남을 때만 한다.
**타임아웃된 생성도 시간을 청구한다**: 멈춘 ComfyUI가 예산 0인 채로 런을 갉아먹으면 안 된다.

타임아웃 자체도 캔버스 면적에 비례하게 했다. 180초는 512×512 한 장 기준이었고, 시트는 픽셀이 최대
6배라 **작업이 시작도 안 된 채** 타임아웃으로 보고된 적이 있다(실제 생성은 59초였다).

## 28. 아직 안 한 것

의도적으로 남겨둔 것들.

**부분 편집 도구 (`replace_lines`)** — 지금은 한 줄을 고쳐도 게임 전체를 다시 생성한다.
출력 토큰이 크고 회귀 위험도 산다. Godot 경로는 파일 단위라 이미 덜하다.

**게임 스켈레톤 템플릿** — 검증된 Canvas 게임 뼈대(루프·입력·상태머신·HUD)를 고정 텍스트로 주면
매번 처음부터 짜지 않아도 된다. 첫 생성 품질에 영향이 커서 별도로 다루는 게 맞다.

**`descope` 액션** — 계약이 애초에 달성 불가능하면 지금은 매 사이클이 같은 자리에서 실패한다.
축소를 허용하면 실패한 런을 작지만 완성된 게임으로 바꿀 수 있다. 다만 두 가지 위험이 있다 —
사람이 승인한 계약을 조용히 줄이는 것, 그리고 **목표를 고칠 수 있는 에이전트는 목표를 고친다**
(버그를 고치는 것보다 요구사항을 지우는 게 항상 쉽다). 먼저 측정이 필요하다: 같은 요구사항이
반복 거부되면 계약 문제, 산발적이면 코드 문제다.

**HTML5 실행 검증** — Godot은 헤드리스로 엔진을 띄워 스크립트 오류를 잡는데 HTML5는 JS 문법 검사뿐이다.
§26이 통과의 의미를 바로잡았지만, *"실행은 되는가"*는 여전히 아무도 묻지 않는다. 헤드리스 브라우저로
터짐·미출력·입력 무반응만 봐도 바닥이 생긴다. 모델 호출은 0회다.

**크로마 언믹싱** — 지금은 1픽셀 침식으로 초록 테두리를 없앤다(`SPILL_EROSION`). 실제로 병사
프레임의 외곽선이 얇아진 게 그 부작용이다. [aldegad/sprite-gen](https://github.com/aldegad/sprite-gen)은
테두리 픽셀에서 키 성분을 **빼내서** 원색을 복원하고 흰 배경에 대해 검증한다 — 침식이 필요 없어진다.

**스프라이트 스타일 일관성** — 서로 다른 *객체*끼리(플레이어와 적과 동전) 화풍을 맞추는 문제는 남아
있다. 같은 캐릭터의 애니메이션 프레임은 §21에서 풀렸지만 그건 한 장 안에 들어가기 때문이고, 객체가
다르면 같은 그림에 넣을 수 없다. 지금은 `house_style`이 모든 자산에 **바이트 단위로 같은 화풍 절**을
붙이는 선에서 막고 있고, §18의 아트 메모리가 프롬프트 수준에서 거든다. 제대로 풀려면 `clip_vision` /
`style_models` 설치가 선행돼야 한다.

**아트 메모리 표본** — 장르당 스프라이트가 아직 한 자릿수다. 예시로 쓸 만하려면 장르당 좋은 것이 2~3개는
모여야 하고, 런 10~20회는 더 돌아야 한다. 구조는 지금 있으므로 **그동안 생성되는 프롬프트가 버려지지는
않는다.**

**평가 전체 기준선** — `evals/briefs.json` 15케이스 순차 실행이 약 15분이라 `baseline.json`을 아직 못 떴다.
케이스끼리 독립이므로 병렬화하면 3분 안쪽이다.
